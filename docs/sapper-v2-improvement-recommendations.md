**HotMouse 借鉴 sapper-v2 的改进建议**

分析日期：2026-11-02。

实施补充：本文末尾第一轮范围的前五项已实现，具体协议、界面入口与验证方式见 [strategy.md](strategy.md)。下文保留分析时的源码比较与建议。

分析范围：HotMouse 当前工作区的 Go 后端、Worker、图协议、前端和测试，以及 sapper-v2 的 Python 核心、提示词、Docker 指挥官与看门狗架构。HotMouse 的分析包含当时尚未提交的工作区内容；sapper-v2 参考提交为 `ba3d3d4`。

本文保存源码对比后的建议，供后续设计与实施使用。建议尚未实现；分析时没有修改业务源码。已有后端测试 `go test ./...` 通过，前端 `npm test` 的 8 项单元测试全部通过。尚未进行真实题目上的得分、耗时和模型成本对比。

**结论：适合吸收 sapper-v2 的部分机制。对 HotMouse 最有价值的是分层记忆、经验检索、比赛预算调度和止损策略。HotMouse 已有的数据库、租约、执行恢复和 CLI 适配，应继续保留并扩展。**

HotMouse 的执行与持久化机制已经比较严谨，目前更值得补的是“如何更有效地安排任务和利用经验”。

**HotMouse 已经具备的能力。** 这些部分与 sapper 的设计有重叠，有些实现还更完整。

| 能力 | HotMouse 当前实现 | 引入 sapper 机制的价值 |
| --- | --- | --- |
| 事实与任务分离 | Fact、Goal、Step、Finding，支持依赖与证据连接 | 已有，无需重建图模型 |
| 并发写入一致性 | SQLite 事务、外键、WAL | 保留现有机制 |
| 任务所有权 | Step、Decide 租约和心跳 | 比 sapper 的领取标记更适合扩展 |
| 执行恢复 | 检查点、会话 ID、待总结、待提交、人工介入状态 | 已有较完整恢复链路 |
| 避免重复执行 | 恢复已保存结果、核对已提交结论 | 比直接重发任务更谨慎 |
| 多 CLI 适配 | Codex、Claude Code、Pi 原生驱动 | 已有，无需换成 tmux 输入注入 |
| 项目上下文 | 默认与项目 YAML 合并 | 可作为策略配置入口 |
| 操作可观测性 | 工作历史、审计、通知、Campaign 和图界面 | 已有产品基础 |
| 分层记忆与检索 | 主要仍是完整图注入 | 很值得补 |
| 比赛资源分配 | 优先级和失败冷却，服务内串行执行 | 值得进一步扩展 |

例如，[ConcludeStep](../backend/internal/core/service.go) 在一个事务中创建结果事实、结束步骤、记录 Finding 并更新漏洞投影。这个机制比 sapper 的多个 JSON 文件依次更新更可靠。

[provider_recovery.go](../backend/internal/worker/provider_recovery.go) 还区分了执行和总结：执行中断后，可以恢复原会话总结已有证据，避免重新执行动作。这一点应该成为后续改造的基础。

**第一项最值得做：把模型上下文与完整图导出分开。**

HotMouse 当前的主要 Decide、Execute 调用使用 [ExportYAML](../backend/internal/core/service.go) 构建上下文，其中包含全部 Facts、Goals、Steps、Hints、Findings，以及完整 `Finding.Data`。

这对早期的小项目很方便，但一个项目积累几十个步骤后，会出现几个问题：

- 每一步都重复读取大量已经结束的工作。
- 长证据和日志挤占当前任务的上下文。
- 重要结论容易被历史细节淹没。
- 执行者不容易区分“当前必须阅读”和“需要时再查”的内容。

sapper 的 `title → description → doc` 三层记忆适合引入 HotMouse。

建议保留完整导出接口，另外增加**专门给模型使用的紧凑视图**：

```text
Decide 上下文
├── 当前目标与完成条件
├── 开放步骤、优先级和阻碍
├── 近期重要事实摘要
├── 相关历史索引
└── 剩余预算

Execute 上下文
├── 当前 Step
├── Step.from 引用的事实
├── 对应 Goal 与项目范围
├── 相关历史摘要
└── 按需读取详细证据的入口
```

这是比“截断完整 YAML”更好的改法。直接截断可能丢掉依赖事实或完成条件；紧凑视图应该优先保证这些信息完整。

具体适配时，可以：

- 保留 `Fact.Description` 作为结果摘要。
- 为事实和步骤补充可选标题、详细记录与元数据。
- 让完整证据继续保存在关联记录中。
- 为模型增加按 ID 读取详情的 CLI/API。

当前 [Fact 结构](../backend/internal/core/models.go) 只有 ID 和 Description，而 Finding 已有标题和结构化 Data。可以先利用这些已有结构，逐步扩展，避免一次重写整个协议。

**适合程度：很高。改动成本：中等。建议最先做。**

**第二项：引入历史检索和跨题经验复用。**

HotMouse 已经保存了证据链，但主要使用方式是读取当前项目的完整图。它还缺少一个明确入口，回答：

> 以前是否遇到过类似任务？哪些做法已经验证有效，哪些已经失败？

sapper 的 `recall` 和共享 KB 在这里有参考价值。不过，HotMouse 可以利用 SQLite 实现，不需要另建一套 JSON 文件存储。

建议分成两种检索：

| 检索对象 | 用途 |
| --- | --- |
| 当前项目事实、步骤、发现 | 避免重复验证和重复走失败路线 |
| 跨项目方法与经验 | 将成熟方法迁移到相似题目 |

两者需要明确区分。跨题复用的是**方法、适用条件和教训**；目标地址、凭据、flag、当前服务状态仍要在新题里重新确认。

一条可复用经验最好包含：

```text
适用条件：什么类型的目标或环境
已验证的方法：做了什么
结果依据：关联哪些事实和证据
失败条件：什么情况下不能套用
来源：哪个项目、哪个步骤
```

第一版用关键词、标签和 SQLite FTS 检索就足够，不必立即接入向量数据库。检索效果经过实际题目验证后，再决定是否需要语义检索。

跨项目知识不适合默认整库注入。每次根据当前 Step 召回少量相关条目，效果更容易控制。

**适合程度：很高。改动成本：中等。建议在紧凑上下文之后做。**

**第三项：补“执行过程中重新评估”的调度能力。**

这是 HotMouse 与 sapper 指挥官架构的一个关键差异。

当前 [RunOnce](../backend/internal/worker/runner.go) 优先恢复或执行已有步骤；`nextDecideProject` 在项目仍有开放步骤时，会跳过该项目的 Decide。

这意味着当前自动循环更接近：

```text
提出一批步骤 → 执行这些步骤 → 队列耗尽 → 再规划
```

它有稳定、容易理解的优点，但会限制中途调整。例如：

- 第一项检查已经推翻了后面两个步骤的前提。
- 某条路线连续没有进展，需要切换方向。
- 新发现的凭据或服务使另一条路线更有价值。
- 当前步骤队列还没清空，但比赛时间已经不足。

HotMouse 的 Decide 返回协议已经支持 `step_updates` 和子目标，具备调整任务的基础；主要缺的是自动触发时机。

建议增加事件触发的重新评估，例如：

- 获得重要新事实。
- 某个目标达到阶段成果。
- 连续若干步骤没有带来新信息。
- 确认某条路线不可行。
- 累计执行时间接近项目共享预算。
- 剩余比赛时间进入收尾阶段。

重新评估可以调整**尚未领取**的步骤，保留现有租约边界。正在执行的任务如需停止，应通过显式取消机制处理，不能让计划更新直接抢占它。

这里也有一个具体接口问题值得一起修：当前模型提示词支持按 `s001` 更新步骤，但 [exportStep](../backend/internal/core/service.go) 没有导出步骤 ID。新增模型上下文时，应提供明确、稳定的 Step ID，保证“看到的任务”和“允许更新的任务”一致。

**适合程度：很高。改动成本：中等。建议作为第一阶段重点。**

**第四项：把失败冷却升级为基于进展的止损。**

HotMouse 已有 `worker_retry_state`、失败退避和拒绝冷却，这些主要处理的是执行层错误。

CTF 中还存在另一类问题：

> 每一步都正常执行并返回结果，但整条路线没有产出。

例如连续生成“继续检查另一个位置”的步骤，进程没有报错，图也在增长，实际上一直在重复探索。

sapper 的止损规则值得借鉴，但不宜直接复制固定的“20 分钟派将军、45 分钟关闭”。这些阈值依赖题目数量、模型和比赛限制。

HotMouse 可以先把执行结果结构化：

| 结果类型 | 调度含义 |
| --- | --- |
| 新事实或阶段成果 | 可以继续投入 |
| 已确认的负面结果 | 缩小搜索空间、调整计划 |
| 目标侧阻碍 | 需要寻找替代路线 |
| 执行环境问题 | 修环境或暂停，不能当作目标结论 |
| 无新增信息 | 累计次数，触发重新评估 |
| 需要人工介入 | 保留证据与检查点，停止自动重复 |

当前 Execute 结果主要是 `description` 和可选 `finding`。建议将“步骤结果类型”与漏洞 Finding 分开，避免把所有失败都包装成普通事实或漏洞记录。

这样调度器就能判断：

```text
这条路线累计花了多久？
获得了哪些新信息？
是否已经重复了已知失败？
继续投入是否比切换方向更有价值？
```

还可以保存“搁置原因、重新开启条件、下一次应尝试的方向”。这会比一个普通 `stopped` 状态更适合长期自动解题。

**适合程度：很高。改动成本：中等。**

**第五项：加入比赛总预算和收尾策略。**

HotMouse 当前的 [WorkerRuntime](../backend/internal/core/worker_config.go) 控制 Decide、Execute、Conclude 的单次超时。这保证了步骤有边界，但不等同于整场比赛预算。

建议增加一层 Campaign 配置，关联多个 Project，保存：

- 持久化截止时间。
- 每题累计投入时间。
- 已取得成果和平台接受结果。
- 题目预估难度或成本。
- 搁置原因。
- 收尾预留时间。

现有 [Campaign 接口](../backend/internal/httpapi/campaign.go) 是单项目的只读综合视图，可以提供部分统计基础，但还不是调度器。

预算应由 Go 程序实际执行。模型可以建议下一步，程序负责校验剩余时间、任务上限和允许的状态变化。截止时间应保存在数据库中，服务重启继续使用原值。

如果是多题比赛，还需要补调度公平性：当前全局步骤按优先级和创建时间选择，并优先于新 Decide 工作。持续有步骤的项目可能长时间占用串行 Worker。可以增加每题时间片、等待时间和累计投入权重。

**适合程度：多题比赛很高；单题自动解题中等。改动成本：中等到较高。**

**第六项：增加专门的 flag 台账与平台适配。**

HotMouse 内置 CTF 模板的目标是取得 flag，但当前没有专门的 flag 生命周期和比赛平台提交接口。

如果希望完成从解题到上分的闭环，这项值得增加。sapper 的“先保存、再提交、再保存回复”思路可以吸收，其提交实现中的缺陷应避免带入。

建议把以下状态明确分开：

```text
captured
→ submission_pending
→ accepted / rejected / submission_unknown
```

`submission_unknown` 很重要：请求超时可能发生在平台已经接收之后，此时应先核对结果，不能直接等同于拒绝或盲目重试。

台账应保存项目、题目编号、来源事实、flag、提交尝试和平台回复。平台适配器独立实现，调用失败分类和状态更新由统一接口处理。

现有 Finding 可以表达 `kind=flag`，但提交尝试和平台状态最好有专门记录，方便对账、去重和恢复。

**适合程度：需要自动上分时很高。改动成本：中等。**

**第七项：按任务选择模型，适合引入，但要尊重当前恢复机制。**

HotMouse 当前基本使用一份 `worker_config`，Decide 与 Execute 读取同一套驱动和环境。可以借鉴 sapper 的分层用模型：

| 工作 | 可考虑的配置 |
| --- | --- |
| 常规整理、短侦察 | 较低成本配置 |
| 全局规划、复杂推理 | 较强配置 |
| 复杂路线复核 | 不同模型或独立验证配置 |
| 中断总结 | 与原会话兼容的配置 |

关键是不能简单在重试时换模型。

HotMouse 已用 [providerIdentity](../backend/internal/worker/provider.go) 检查恢复配置是否匹配。后续每个执行尝试应该保存使用的模型配置；恢复总结继续采用原配置，切换供应商则建立新的执行尝试，并读取已有证据。

可以先做按阶段配置，随后再根据任务难度和效果自动选择。没有运行数据之前，不宜假定更贵模型一定更划算。

**适合程度：高。改动成本：中等。**

**多 Worker 并发有价值，但属于较大的后续改造。**

如果主要场景是许多独立题目，并发会直接影响吞吐量。HotMouse 的租约和事务为此提供了基础，比较适合逐步扩展。

不过，当前这些地方都明确围绕单 Worker 设计：

- 全局 `WorkerMu` 覆盖执行过程。
- `worker_config` 是单行配置。
- 一个默认 Worker 名称。
- 每个项目一个工作目录。
- 可观测性接口明确返回 `worker_mode=single`。

所以不能只删除 Mutex，再启动几个 goroutine。

建议先做**跨项目的小型工作池**，并保留“每项目同时一个执行者”的默认限制。需要唯一执行身份、任务配置快照、资源上限、进程取消和可靠的租约领取。等跨题调度稳定，再考虑同题多个执行者分工。

同题并发还要处理文件覆盖、重复尝试、共享工具与目标资源竞争。收益需要用题目验证，不能只以创建了多少 Agent 衡量。

sapper 的 tmux 可以作为观察窗口，但 HotMouse 的 Go 进程管理、检查点和结构化 API 更适合作为控制基础。

**有几项机制建议继续沿用 HotMouse 自己的实现。**

| sapper 中的机制 | HotMouse 的适配判断 |
| --- | --- |
| JSON 文件作为图存储 | 继续使用 SQLite 和事务 |
| tmux 输入消息作为主控制协议 | 继续使用结构化任务与 API |
| 崩溃后重新发送原始任务 | 保留检查点和“只总结已有证据”的恢复方式 |
| 固定角色名和时间阈值 | 提炼成可配置策略，按实际题目校准 |
| 每次加载长篇军规 | 放入版本化策略，控制注入体积 |
| 仅靠文字判断成果可信度 | 使用证据和验证记录，文本评分只辅助展示 |

分层记忆引入后，应明确标记图、目标输出和历史资料属于数据。当前 [decidePrompt、executePrompt](../backend/internal/worker/runner.go) 主要强调返回协议，可以补充这些内容的来源和使用边界，防止目标文本或旧经验覆盖当前任务规则。

**建议的第一轮改进范围与后续顺序。**

1. 新增紧凑模型上下文，完整 YAML 导出继续保留。
2. 增加结构化执行结果，区分进展、负面结果、阻碍和环境失败。
3. 增加事件触发的 Decide，让系统能中途调整尚未领取的步骤。
4. 增加每条路线累计投入与止损记录。
5. 随后做历史检索、跨题经验库和 flag 台账。
6. 多题场景再接入 Campaign 总预算与小型并发工作池。

这一轮应以真实题目的**成功数、有效耗时、token、重复动作次数和恢复后的重执行次数**验收。源码已经说明这些机制能接入 HotMouse；究竟先带来多少收益，还需要固定题集和模型做前后对比。
