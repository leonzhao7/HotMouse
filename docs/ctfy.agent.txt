This is the contract between ctfy and a container it dispatches. If you are writing an agent to run on this platform, this page is the whole interface — everything else is your own design.

The platform makes no assumption about what is inside your image: no language, no framework, no base image, no entrypoint convention. It starts your container, tells it what to do, and reads one file back.

1. What you receive
1.1 Environment
variable	meaning
CTFY_PLATFORM_URL	base URL of the API, e.g. https://ctfy.example
CTFY_TOKEN	your bearer. Send as Authorization: Bearer $CTFY_TOKEN
CTFY_EVAL_CHALLENGE_ID	which challenge
CTFY_EVAL_COMPETITION_ID	which competition (may be empty)
CTFY_EVAL_TARGET_INSTANCE	the instance the platform already started for you — the same id as target_instance in task.json. Absent for a qa item, which has none
CTFY_TARGET_URL	the target's one web endpoint (http://host:port), when it has exactly one — the same address as in target_endpoints. Absent with no target, no web endpoint, or more than one
CTFY_EVAL_MAX_TURNS	soft budget for your own agent loop. Absent means no budget
CTFY_WORK_DIR	your working directory (/ctfy/work) — the briefing is in it, and your result goes back in it
LLM_FLAVOR	anthropic or openai — which wire protocol
LLM_API_KEY	the key to use. May be a per-run handle, not an upstream key
LLM_MODEL	the provider model id to request
LLM_BASE_URL	endpoint override; absent means the SDK default
CTFY_EVAL_DRY_RUN	1 when this run is a check of your image, not a task. Absent otherwise — see §3.1
⚠️ LLM_API_KEY may be empty. That is a real state, not a bug: it means nothing is funding this run. Fail loudly rather than falling back to a key of your own — a run that quietly spends somebody else's account is worse than a run that stops.

⚠️ LLM_BASE_URL and LLM_API_KEY are one decision. If a base URL is given, use it: sending the key to the model row's default endpoint spends it somewhere it is not valid, and the failure comes back looking like a bad credential.

⚠️ A hosted run must reach its model through LLM_BASE_URL. The gateway behind it is how the run is funded and counted. A run that exits 0 having made no call to it — a hard-coded provider URL or key, reading other names than these (or than the SDK names below for your LLM_FLAVOR), or exiting before the first call — is recorded errored with that reason, and its page shows your exit code and the end of your output beside it. It is not a credential problem unless the run was paid for with your own key.

The same three values, under your SDK's own names
You do not have to read any of the four names above to build a client. The platform also sets the variables the provider's own SDK already reads, so an agent written the ordinary way works with no ctfy-specific code at all:

from anthropic import Anthropic
client = Anthropic()           # key and base URL come from the environment
Which set you get is decided by LLM_FLAVOR:

LLM_FLAVOR	key	base URL	model
anthropic	ANTHROPIC_API_KEY + ANTHROPIC_AUTH_TOKEN	ANTHROPIC_BASE_URL	ANTHROPIC_MODEL
openai	OPENAI_API_KEY	OPENAI_BASE_URL	OPENAI_MODEL
Five things about them:

The anthropic key arrives under both names, and that is not redundancy. The SDK turns ANTHROPIC_API_KEY into an x-api-key header and ANTHROPIC_AUTH_TOKEN into a bearer. Anthropic's own endpoint accepts either, so one name was enough for years — but an Anthropic-compatible endpoint authenticates the bearer, and a run carrying only the first arrives unauthenticated and is told it is not logged in, which reads as a missing account rather than as a key sent under the wrong name. Read whichever your client expects; they carry the same value.
You get one provider's names, never both. A run is funded for one flavor; the key is not valid at the other's endpoint. Libraries that pick a provider by which variable happens to be set would otherwise be choosing by coin flip.
The model variable is a convenience, not a guarantee. Neither official SDK takes a model from the environment — ANTHROPIC_MODEL is read by Claude Code, OPENAI_MODEL by parts of the wider ecosystem. LLM_MODEL is the one to read if you want the platform's answer.
On anthropic, the model is published under every slot a Claude-Code-compatible client resolves through, all carrying the one value the platform chose: ANTHROPIC_MODEL, ANTHROPIC_DEFAULT_OPUS_MODEL, ANTHROPIC_DEFAULT_SONNET_MODEL, ANTHROPIC_DEFAULT_HAIKU_MODEL, ANTHROPIC_SMALL_FAST_MODEL and CLAUDE_CODE_SUBAGENT_MODEL. A client that resolves a tier rather than a model — asking for "the fast one" — reads a slot the run was never funded for if that slot is unset, and silently spends against a model the platform did not pick. Setting them all means every route to a model arrives at the same one.
An unset value stays unset. An unfunded run does not arrive as ANTHROPIC_API_KEY=""; the variable is simply absent, so your SDK raises its own "no key" error instead of sending an empty header and getting back a 401 that reads like a revoked credential.
LLM_FLAVOR has no equivalent and never will: it answers which SDK to construct, which is the one question a provider's own SDK never has to ask. Read it if you support both.

Config files for the CLIs that ignore those names
Codex and pi read neither base URL above, so when LLM_BASE_URL is set the platform also writes their config files into your user's $HOME before you start:

CLI	file	what it says
Codex	~/.codex/config.toml	provider ctfy at LLM_BASE_URL, wire_api = "responses", key from env_key = "LLM_API_KEY", model and model_context_window when set, and the platform's MCP server with bearer_token_env_var = "CTFY_TOKEN" — openai flavor only
pi	~/.pi/agent/models.json, ~/.pi/agent/settings.json	provider ctfy at LLM_BASE_URL with "apiKey": "$LLM_API_KEY", the model, and that model as the default
So codex exec "$(cat README.md)" and pi -p "$(cat README.md)" need no flags and no wrapper. Four rules:

Your image wins. A file your image already ships at that path is left alone, and nothing is merged into it.
No credential is written. The files name LLM_API_KEY and CTFY_TOKEN; the CLI reads them from the environment at request time.
Owner-only. Files are 0600 and any directory created is 0700, owned by your image's USER. With no known home (a numeric USER with no passwd entry and no HOME), nothing is written.
Not on a dry run, and not without LLM_BASE_URL: there is nothing to point at.
1.2 The working directory — /ctfy/work/
One directory, writable. Three files are in it when you start; the second is generated from the first, so they cannot disagree.

/ctfy/work/task.json    the contract, machine-readable
/ctfy/work/README.md    the same thing as prose, for a model to read
/ctfy/work/mcp.json     an MCP client config for the platform's own tools
/ctfy/work/attachments/ the challenge's files, when it has any
/ctfy/work/result.json  ← you write this (optional, §3)
The challenge's files are already here. When a challenge ships attachments, the platform copies this run's own copy — the files your target instance rendered, which for a challenge with per-team files differ from every other team's — into attachments/ before you start, and task.json lists them:

"attachments": [
  { "name": "crackme", "size": 14120, "path": "/ctfy/work/attachments/crackme" },
  { "name": "dump.bin", "size": 9000000, "path": null }
]
path is null for a file that was not copied — the copy is bounded at 4 MiB per run — and README.md then gives the call that downloads it (GET /api/v1/instances/{target_instance}/attachments/{name}).

⚠️ One address, deliberately. This used to be two — a read-only briefing directory and a separate writable one for the result — which meant an agent had to learn two of our variable names before it could do anything. Every address we require is adaptation somebody else has to do to enter one event, so there is now one, and where the result goes is derived from it rather than told.

It is also your working directory. The platform starts your container with its cwd set here, so an agent that simply reads the files around it needs to know nothing at all — no variable, no path. $CTFY_WORK_DIR is for images that would rather be told.

⚠️ So your entrypoint must not depend on your own WORKDIR. ENTRYPOINT ["python", "agent.py"] resolves that filename against the working directory and will not start; write ENTRYPOINT ["python", "/app/agent.py"]. ctfy agent check says so before you register, and the dry run refuses such an image outright. The same applies to data your program opens by a relative path.

mcp.json — the platform as tools, not as HTTP
The whole player API — registering, listing challenges, starting and renewing instances, submitting answers, reading the scoreboard, and on an AWD+ run the captured traffic — is served as MCP tools at /api/v1/mcp/, authenticated with the same bearer. mcp.json is that address in the shape every MCP client reads, so the integration is one flag:

claude --mcp-config "$CTFY_WORK_DIR/mcp.json" -p "$(cat "$CTFY_WORK_DIR/README.md")"
Uploading a challenge over this endpoint: pack it locally and send archive_base64. The tools check_authored_challenge, upload_authored_challenge and revise_authored_challenge take the tree in one of three forms. Over /api/v1/mcp/ the platform cannot read your disk, so path is refused there (it is for a local stdio ctfy mcp only); pack the directory on your machine with tar czf - <dir> | base64 -w0 and pass the output as archive_base64 (HTTP only). files (path to text) works on either transport but puts exploit source in the request body as plain text, which a network filter in front of a deployment may block before the platform sees it — do not use it for source over HTTP.

You are not obliged to use it. The REST API is the contract and the tools are a projection of it; use whichever your agent is built around. If yours speaks no MCP, every route in this standard is an ordinary HTTP call carrying the bearer you already have:

curl -sS -X GET "$CTFY_PLATFORM_URL/api/v1/me" \
  -H "Authorization: Bearer $CTFY_TOKEN"
That one answers with your account and the competitions you are in, and is the cheapest way to check the token works before spending a turn on anything else. Every path below is under $CTFY_PLATFORM_URL/api/v1.

⚠️ The bearer is written as ${CTFY_TOKEN}, not as its value. No credential is ever written into this directory — the token is in the environment, where it already is, and a second copy is a second place to leak it from. Clients that expand ${VAR} in a config (Claude Code among them) need nothing further; if yours does not, substitute it yourself, or the platform answers 401 and it will read like a revoked token rather than an unexpanded string.

⚠️ A dry run gets no mcp.json at all, because it has no platform and no token (§3.1). Its absence is the honest signal; a config pointing at nothing would cost you a run's worth of connection errors.

Branch on task.json's run_mode if you want to specialise. You do not have to: README.md is rendered from task.json per mode, so an agent that simply reads it and does what it says is conforming — see §3.2.

⚠️ The briefing is a snapshot, not the whole task. Read §2.

What happens to this directory after you exit
Whatever is in /ctfy/work when your container stops is collected into an archive — along with your Claude Code session, if you leave one where the CLI puts it, and everything you wrote to stdout and stderr. The person who registered the agent can download that archive and read it in the browser.

That is the point: a run used to be able to say what it scored and what it said, and what it wrote down died with the container. Notes, scratch scripts, scan output and half-finished exploits are how somebody works out why their agent did what it did.

⚠️ So do not write your own credentials here. Not your API keys, not a copied ~/.aws, not a token you minted for a service of your own. The platform never writes one into this directory (see mcp.json, above) and neither should you: the directory outlives the container now.

⚠️ It is the run's owner who reads it, and nobody else — not other entrants, not their team-mates. But "nobody else" is a statement about this platform's access rules, not about your secrets: a credential you leave here is one you have handed to whoever operates the deployment you entered.

Collection is best-effort and silent. It never fails your run, it never changes your exit status, and there is nothing to opt into or out of.

2. The five run modes
run_mode is derived by the platform from the challenge and the competition. You are never asked which one you support — you are told which one this is.

It is the same decision the platform's own harness picks its tool table from (one function, resolve_run_mode), so what this field says and what the run actually is cannot come apart.

instance — a jeopardy challenge with infrastructure
{
  "schema_version": 3,
  "run_mode": "instance",
  "challenge": { "id": "CTFARENA-001", "name": "DocuVault", "description": "…" },
  "competition_id": "arena",
  "questions": [ { "id": "flag", "prompt": "The vault master secret" } ],
  "gated_questions": 2,
  "scope": [],
  "rules_of_engagement": [],
  "deliverable": "an answer per question, submitted to POST /api/v1/submissions",
  "platform_url": "https://ctfy.example",
  "max_turns": 40,          // null when no budget was set — never 0
  "result": { "path": "/ctfy/work/result.json", "stdout_fallback": false },
  "target_instance": "3f9c…",
  "target_endpoints": [     // omitted until the target reports its surface
    { "label": "web", "type": "http", "url": "http://3f9c.ctfy.example:80" }
  ]
}
The platform has already started your instance — target_instance names it, and target_endpoints lists the addresses a player is shown for it (type is http, https, tcp, udp or ssh; a raw socket's url is host:port). One web endpoint is also $CTFY_TARGET_URL. The full record, credentials included where the challenge has any, is GET /api/v1/instances/{target_instance} (or get_instance over MCP). Attack it, and put your answers in result.json (§3, the short way) or submit them as you go — a plain web challenge needs no platform call at all, except to re-read the questions gated_questions says are hidden. Those published endpoints are what your container may reach: the worker that runs you is not necessarily the one that runs your instance, and the platform opens exactly the addresses a player is shown.

⚠️ Do not call POST /api/v1/instances. Since version 3 your token cannot start an instance at all (403 token_missing_scope): the platform starts the target for every run, sizes its lifetime to the run and takes it down afterwards. Your token also reaches only this run's challenge — reading or submitting for any other answers 403 token_challenge_forbidden.

⚠️ gated_questions is the field that catches people out. A challenge's later questions are gated behind requires: — their prompts do not exist yet, and the platform deliberately will not paraphrase them. If this number is above zero, re-read GET /api/v1/challenges/{id} after every correct answer. An agent that reads only task.json, answers question one, and stops has scored a fraction of what it could and looks like it gave up.

qa — a question with no infrastructure
413 corpus items (SecQA, MMLU-CS, CTI-MCQ) are pure multiple choice. There is no instance to start. Answers go to POST /api/v1/qa/submissions.

There is no target and none is coming: target_instance is null and CTFY_EVAL_TARGET_INSTANCE is absent by design, not because something failed. Everything you need is the description, the questions and — for an item that ships files, such as an archive to inspect — the files already in attachments/ (§1.2). An image that exits here without calling its model is recorded errored as a challenge with no environment; if it has a reason, put it in stop_reason (§3) and the run page shows it.

defence — AWD+
You are given a box that is yours to defend. The deliverable is a patch submitted to POST /api/v1/patches.

⚠️ That endpoint returns a receipt, not a verdict. pending means it was accepted for judging. Treating it as a result makes an agent resubmit and hit the outstanding-patch cap.

awd — a classic attack & defence match
Every team runs an identical copy of one gamebox, and yours is already running — the organiser started it before kickoff and you do not start, stop or reset it. A fresh flag is planted in every box each round.

Two things are scored, and they pull against each other:

Attack. Capture flags from other teams' boxes and bank them with submit_awd_flags. A flag from an earlier round is dead, so check get_awd_match before spending turns on a long exploit.
Defence. You lose points when somebody takes the flag from your box, and you lose more if it stops serving — a checker probes it every round. Defence is done the way a human plays this format: get a shell on your own box and fix it in place. A patch submitted to POST /api/v1/patches is judged against a sandbox copy and changes nothing about the box being probed and scored.
How long you run — you are started once, not once per round
A match runs many rounds — get_awd_match tells you tick_count and tick_seconds, so the match ends at starts_at + tick_seconds × tick_count. You are started one time and you are not restarted. The platform does not dispatch a fresh container each round, so if your process exits, your match is over — even if rounds remain.

Keep working until the last round. Loop: attack, defend, and re-check get_awd_match; when a round rolls over every flag you were holding is dead, so re-take the boxes you took and confirm your own patch survived. Do not exit after one pass. If you write a result.json and stop while the match is still on, that file does not end the match gracefully — it ends your participation early while every opponent keeps capturing.

⚠️ A run that ends before the match's last round is recorded incomplete, not succeeded. The platform reads its own clock at the instant your process finishes; leaving early is a property of your image, not of how the match went, and the run row says so. This is the one obligation that separates a match from every other run mode, where finishing your work is the end of the run.

Getting that shell
Ask by naming the match — the box is your team's and the organiser started it before kickoff, so the competition is enough to find it:

curl -sS -X POST "$CTFY_PLATFORM_URL/api/v1/competitions/$competition_id/awd/ssh" \
  -H "Authorization: Bearer $CTFY_TOKEN"
or get_ssh_credential(competition_id=...) over MCP. For a box you started yourself — outside a match — the same credential is at POST /api/v1/instances/{instance_id}/ssh, where the instance id is a thing you actually hold because you created it.

The credential carries an exposure field, and it decides how you connect — a match runs one of two shell transports, chosen by the organiser:

managed (the default) — the platform mints a throwaway keypair, a certificate, a username, and the bastion's host and port. Write the two files out, chmod 600 the key, and connect through the bastion:

ssh -i key -o CertificateFile=key-cert.pub -p "$port" "$username@$host"
open (classic AWD) — there is no bastion and no certificate. sshd runs on the gamebox itself, on the game network, so the credential is a plain login: { "exposure": "open", "username": "root", "password": "...", "host": <the box's arena address>, "port": 22 }. Connect straight to the box over your arena tunnel:

sshpass -p "$password" ssh -o StrictHostKeyChecking=no "root@$host"
Two things follow from open that do not hold for managed:

Every team in the match can reach every box's sshd — that is the game. Gaining SSH to a rival's box, through a credential they failed to rotate, a weak config, or a vuln, is itself an attack: once in, you read that round's flag off /answers/flag and submit it the ordinary way. When the match ships a fixed default credential, every team starts knowing it (the platform's default is changeme), so a rival who has not rotated is a walk-in. When it ships a per-box random one, only the owner is told it (through get_ssh_credential), and a rival must earn access.
Defending starts with your own sshd. Rotate the starting password the moment you are in — appctl passwd <new> on the gameboxes this platform ships — and harden the box. A rotated-out password locks out any new rival login; a session a rival already holds persists until it disconnects.
Once you have a shell in a box, inside the app container it is full-open: you may read the current round's flag, break the service (which costs the owner their SLA — a real DOWN), and plant persistence or backdoors. The platform does not police what happens inside the app container. The one thing that shell can never reach is the groundtruth: it opens in the app container, which holds only this round's minted flag (exactly what the service already serves), never the checker's or rotator's answers for every round, and never the control plane — the arena is a closed WireGuard mesh of this match's teams and the platform alone.

⚠️ Your image needs an SSH client. Nothing else in this standard requires one, so an image built for the other four modes very likely has none — and the failure is a match spent unable to defend. Install openssh-client (or equivalent) if you intend to enter a match; add sshpass too if you expect an open-exposure match, where the credential is a password rather than a key.

What an image must bring to a match, all of it on your side of the wire — the platform installs nothing into your container:

An SSH client (ssh, e.g. openssh-client) — the only way onto your own box, so without one you can attack and cannot defend.
An HTTP client (curl or your language's own) — the platform's API if you do not use MCP, and the one way to check your own service still answers: request your own box's address (the get_awd_targets row marked is_own) from your container, which is how other teams reach it. Do not assume your shell can reach it; in some gameboxes it opens in a separate container that shares only the source files.
What you are told about the box, you are told by the challenge. get_challenge carries a defence object, read from the gamebox's own declaration: shell_service (where your shell opens), shell_is_scored (whether that is the service being attacked and probed), live_files (the file to edit, and where its shipped original is kept) and restart_command — the command that makes an edit take effect. A running service keeps the code it loaded, so an edit does nothing until you run that command. Nothing restarts the service for you: if it dies — because your edit broke it, or because an attacker crashed it — it stays down, and you lose SLA every round, until you bring it back with that command. An empty restart_command means the gamebox does not say how an edit takes effect, never that it happens by itself.

The gameboxes this platform ships open your shell in the scored service on an ordinary Linux toolset (bash, ps, ss, curl, lsof, an editor), with appctl status|start|stop|restart|logs controlling the service.

Three things, in the order they will bite you:

The credential expires in minutes, and deliberately: it covers connecting, and the session it opens outlives it. Ask for a new one per connect rather than caching. A session is dropped after 30 minutes idle and 4 hours in total, so a long match means reconnecting.
You do not need your box's id, and in a match you should not reach for one: a gamebox is identified by its address and its owning team, which is what GET /api/v1/competitions/{id}/awd/targets publishes (your own row is marked is_own). There is no instance id in that listing and none is needed. An id that is not yours is refused as if it did not exist.
Only change what you must. The checker probes your service every round; breaking it while patching costs more than the attack it prevented.
⚠️ This is the one mode where the platform's own built-in harness cannot do everything you can. It has no shell, so it can attack a match and cannot defend one. That is a stated bound rather than an oversight — it is a scripted solver, and a shell is the whole point of bringing your own image.

⚠️ There is no question list, and its absence is deliberate. Every other mode names what to capture; a match has nothing to name. Start with get_awd_targets — a gamebox publishes no ports and the match network is internal, so the addresses it returns exist nowhere else and cannot be derived. Your own box is in that list marked is_own; a flag taken from it is always refused.

Reaching the arena from outside the platform
A container the platform dispatched is already on the match network; the addresses get_awd_targets returns resolve from it and there is nothing to set up. An agent running anywhere else — your own laptop, your own host, a runner you brought — is not, and the same addresses reach nothing, because a gamebox publishes no ports and the match network is an internal bridge.

join_awd_arena (or POST /api/v1/competitions/{id}/awd/vpn) is the door. It returns a complete wg-quick file:

wg-quick up ./arena.conf     # the file the call handed you
Four things worth knowing before you wire it up:

It routes the match's network and nothing else. The rest of this machine's traffic is untouched, so bringing it up will not take your internet away.
Two key-custody modes. Send your own public_key and the platform never sees the private half — the file then carries a placeholder for you to fill in. Send nothing and the platform mints a pair and returns it once; private_key_included says which you got, so you never have to scan the text to find out.
Your team needs a box in the arena first. The peer terminates on the node holding it, so this is refused with awd_no_box until provisioning has run.
Revoking lands on the next round, not on the call — the peer lives on a worker's WireGuard device and the platform reaches it through the round's own push.
When it does not work, ask test_awd_arena_link before guessing. It puts the three questions to the worker now — handshake, a small ping, a full-size one — and they need three different repairs: no handshake is NAT, a firewall on the UDP port, or a wrong address; a handshake with no ping is a live tunnel whose far end filters ICMP; small packets through and large ones not is a path that cannot carry the tunnel's MTU, which is the one failure nothing else can see — wg show is perfect and every larger response hangs. Rate limited, because it makes the platform dial out to a worker.
To find out whether you are already on, ask get_awd_arena_peer (GET on the same path) — never join_awd_arena. Joining is idempotent in its address and deliberately not in its key, so calling it to check takes down the tunnel you were checking on. The read changes nothing: it answers an absent peer when you hold none, and otherwise your address, your node, and the same file with a placeholder where the private half goes. This is what an agent wants after a restart.
⚠️ You do not need this if the platform dispatched you. Calling it from inside a dispatched container is not harmful, only pointless: you are already on the network the file would route you to.

engagement — a GAUNTLET range
An enterprise estate, tested as one engagement. There is no question list, and its absence is deliberate: a range is scored silently, so the platform will not tell you what it is looking for. You are given a scope and rules, and you are judged on one document.

{
  "schema_version": 3,
  "run_mode": "engagement",
  "challenge": { "id": "GAUNTLET-FIN-001", "name": "Meridian Financial", "description": "…" },
  "questions": [],
  "gated_questions": 0,
  "scope": ["edge.meridian.test", "10.20.0.0/16"],
  "rules_of_engagement": ["Stay inside the scope listed above…", "…"],
  "target_instance": "3f9c…",   // the range is ALREADY RUNNING — see below
  "deliverable": "one engagement report, saved to PUT /api/v1/competitions/{competition_id}/challenges/{challenge_id}/report"
}
⚠️ target_instance is the one field that changes what you do first. When it is present the platform started the estate before it started you, and this container already reaches it — the hosts in scope resolve from here. (The platform reads the player's own VPN access for the estate and puts the tunnel beside your container, on whichever worker runs you; you open nothing yourself.) Do not call POST /api/v1/instances. That would start a second estate, spend your team's instance budget on it, and leave you testing something this container cannot reach: a transcript full of connection errors that reads as a model that gave up. Since version 3 every run with a target carries it, and your token cannot start one anyway.

This is why an engagement no longer needs a VPN tunnel. It used to: the estate is an internal network, and an agent that started it mid-run had to dial back into it. Reversing the ordering removed both the tunnel and the userspace WireGuard terminator every image had to carry to use it.

The report is revisable — PUT replaces, and the last version saved before the window closes is what is graded. Save early and often; a run that dies with an unsaved report has delivered nothing.

⚠️ Write the report as a penetration-test deliverable: what you did, not only what you found. The platform extracts evidence from the prose on every save, so findings you describe concretely score as you write them.

3. What you return
Write JSON to result.json in $CTFY_WORK_DIR — the directory you read the briefing from (/ctfy/work/result.json).

{
  "schema_version": 3,
  "answers": { "flag": "ctfy{...}" },   // hand them over and the platform submits
  "solved": ["flag"],           // question ids you answered correctly
  "fully_solved": false,
  "turns": 17,
  "tool_calls_made": 41,
  "input_tokens": 120000,
  "output_tokens": 8000,
  "stop_reason": "done",
  "writeup": "## What I did\n\nThe vault's `/api/doc/:id` ..."   // optional
}
answers — the short way
You do not have to submit anything yourself. Put what you found in answers, keyed by question id, and the platform submits each one for you when your run ends — through the same grader a human's submission goes through, including the per-question wrong-attempt cap.

{ "schema_version": 3, "answers": { "flag": "ctfy{...}" } }
⚠️ Submitting during the run is still the richer option, and for two reasons that no post-run pass can give you: you learn whether you were right in time to try something else, and questions that are gated only unlock once an earlier one is answered — a run that reports everything at the end never sees them.

⚠️ solved is not how you score, with or without this. The platform writes that field from its own record of what you submitted; a question id listed there that nothing was submitted for is simply not true, and is reported as such.

⚠️ stdout is not read for a user-supplied image, and this is the most important sentence on this page. stdout is yours: log whatever you like to it. The platform's own images retain a legacy stdout fallback; yours does not, because that fallback parses the whole of stdout as one JSON object — so a single log line destroys the result, and it is reported as "produced no JSON rollup", which reads like the model gave up rather than like the plumbing did. It was the first thing every uploaded image hit.

task.json's result.stdout_fallback states which applies to this run. Do not infer it.

Every field is optional, schema_version included — the platform reads what it needs and ignores the rest. Omitting the version is an advisory finding on the conformance check rather than a refusal, because it costs nothing today and everything on the first breaking change, which is exactly when nobody will be able to tell which images were affected.

writeup is your own account of what you did, in markdown, and it is the one field written for a person rather than a counter. Before it existed the platform knew that a challenge was solved and had no record anywhere of how, for every run that was not an engagement.

⚠️ It is not a submission channel and never becomes one. Scoring rides POST /submissions, which carries a per-question wrong-attempt cap for bounded answer spaces; prose carries no such thing. Quoting a flag here scores nothing — submit it. Nothing in the write-up is read by any grader, so it costs you nothing to be candid about what did not work.

Long ones are cut, not refused — a run that answered every question must not fail because its prose ran long — and the cut says so in the text.

3.1 Dry runs
Before an operator reviews your image, the platform can run it once just to see that it starts and honours the contract above. Such a run carries CTFY_EVAL_DRY_RUN=1 in the environment and "dry_run": true in task.json, and its README says so at the top.

Nobody is scoring it. The cheapest correct response is:

{ "schema_version": 3, "solved": [], "fully_solved": false, "stop_reason": "dry_run" }
…written to $CTFY_WORK_DIR/result.json, then exit 0.

⚠️ It passes on a clean exit or a written file. Exit 0 passes whether or not you wrote result.json — the same rule a scored run's status follows (§3); a missing file is shown as advice. An image that writes its file and then exits non-zero passes too. Only an image that does neither fails: it showed nothing.

⚠️ Ignoring the flag is not a failure. An image that goes off and attempts the task anyway still passes by the same rule — the flag is a courtesy that makes the check fast and free, not the thing being tested. Requiring it would fail every image written before it existed.

⚠️ A dry run has no credentials and no platform to talk to. CTFY_TOKEN and LLM_API_KEY are absent and platform_url is empty. That is deliberate: there is nothing to submit and nothing to spend, and a check that handed an unreviewed image either would be giving it exactly what review decides about. Handle it the way §1.1 already asks you to handle an empty key — fail loudly, after writing your file.

The run's status reads your exit code and nothing else. Exit 0 when the run completed — whether or not anything was solved, and whether or not you wrote result.json. What it scored is the platform's own record: the answers you submitted during the run, plus the answers in your file, which the platform submits for you. A run that did neither is recorded as finished with nothing to grade — a result of zero, not a failure.

A non-zero exit means your harness crashed, and the run is recorded as failed regardless of what you wrote; its reason is the end of your stderr, or of your stdout when stderr is empty. A timeout or a cancel is recorded as failed too. The counters in your file (turns, token counts) are still read, so a crashed run's cost is not lost.

⚠️ The file is still worth writing, and the platform still does not go looking at your stdout for it. The run page tells the run's owner when a clean exit wrote no file and submitted nothing, and when a file was written but could not be read (not JSON, too large, not an object) — that run still finished; its answers and counters were not read.

⚠️ A FLAG{...} printed on stdout scores nothing. If one appears there and was never submitted, the run page says so — as a count, not the string — and that is all: stdout is yours, and printing is not submitting.

⚠️ Anything that happens before your container starts — the image pull, the VPN tunnel, the sandbox's firewall, the estate's resolver, the range coming up — is the platform's, never your run's: it is retried (on another node where one fits; a running range is kept and only your container moves) and, if it never succeeds, recorded as errored or unservable, outside your score.

3.2 The smallest conforming agent
There is no minimum sophistication here. The whole contract is three steps, and an image that does only these is a conforming CTFY-0001 client:

Read $CTFY_WORK_DIR/README.md and do what it says.
Write {"schema_version": 3} to $CTFY_WORK_DIR/result.json. Even {} conforms; the version is what makes the first breaking change diagnosable, so write it.
Exit 0.
Everything else on this page is there so an agent that wants to do more can: run_mode if you want to branch on the shape of the task rather than read it, the counters if you want your runs comparable to others', writeup if you want a record of your reasoning, CTFY_EVAL_DRY_RUN if you want the conformance check to be instant.

Step 2 is how the run says what it cost and hands over answers it did not submit. An image that does the work, submits as it goes and writes no file still finishes — but its counters are not read, and an answer it only printed scores nothing, because stdout is not graded.

3.3 Rounds — when the platform starts you again
A hosted instance or qa run may start your image more than once. After a clean exit (0) the platform grades the round — what you submitted and the answers your file handed over — and starts you again in the same working directory, against the same target, when that grading changed what you can do:

a question behind another one became visible; or
an answer you submitted was wrong and that question still allows another attempt.
The next round's README.md says which round it is, lists the questions visible now, and gives each question of the last round a verdict: correct, wrong, not answered, or newly unlocked. It never repeats a submitted value. Everything you left in /ctfy/work/ is still there, except result.json, so a later round can read its own notes; write result.json afresh each round.

There is one clock: every round spends the run's single time limit, and only the time spent running your rounds counts — not the target's start and not the grading between rounds. No round starts with less than a minute left, after a non-zero exit, once everything visible is solved, or past the platform's round limit (at most 5 unless the platform says otherwise). A run that is told nothing new ends after one round, exactly as before. The counters of every round are added up.

You need not do anything to support rounds: a conforming client is started, reads its README and works as it always did.

4. What the platform guarantees, and what it does not
Guaranteed

Your image runs with all capabilities dropped and no-new-privileges, under resource bounds the operator sets, by default (8 GiB of memory, 2 CPUs, 512 pids), on a network that reaches the platform, the model gateway and your target. limits in task.json states the bounds this run actually has.

The exact bytes an operator approved are what run — approval records a digest, and dispatch pulls that digest. Moving a tag afterwards does not change what runs.

task.json gains fields compatibly within a schema version; a breaking change bumps schema_version.

What you leave in /ctfy/work, your Claude Code session and both console streams are collected after you exit and are readable by the run's owner — and by nobody else on the platform (§1.2). Collection never fails your run.

Every read you might repeat says when repeating it is worth a request. An instance's status carries poll_after_s (and a Retry-After header): a few seconds while a start is young, longer as it runs on — a large estate takes tens of minutes — and longer once the box is ready. A competition's scoreboard carries Retry-After too: it is recomputed at most that often whoever asks. The SDK's instances.start and the MCP start_instance already wait this way; a loop of your own should sleep what the platform says, since every team in the event shares one platform's request budget.

An event played in sessions is closed between them, and the platform says so in a way you can act on. Every door that makes progress — start, reset, submit — answers 403 with code competition_paused and a body carrying next_session_starts_at (the ISO instant play resumes) and retry_after_s. That is a wait, not a failure of the challenge: sleep until then rather than polling (a poll spends your model budget and proves nothing), and do not give up. Anything still running when a session ended was stopped (stop_reason session_ended), so start it again in the next one; solves you already earned are kept. Code competition_not_in_session is the other answer: it means no session remains and the event is over. GET /competitions/{id} states play_open, current_session_ends_at and next_session_starts_at beforehand, and an organiser may extend a running session by minutes, so treat current_session_ends_at as a lower bound.

Not guaranteed

That stdout is read (see §3).
That the whole task is in task.json (see §2, gated_questions).
That a key is present in LLM_API_KEY (see §1.1).
That anything else is reachable. Today the run's network also routes to the internet, but a deployment may close that — an event that forbids internet access during play will — so install what your agent needs into the image rather than fetching it at run time.
That max_turns is a number. It is null when no budget was set, and deliberately never 0 — 0 would read as "take no turns" in the most natural loop anyone writes.
Any entrypoint or user. The working directory is now set — it is $CTFY_WORK_DIR — so an entrypoint that resolves a relative path against your own WORKDIR will not start.
That a tunnel helper is there. If the platform ever mounts one it lands read-only at /usr/local/bin/wg-socks — and that mount is inert on every deployment today: nothing resolves a helper to pass, so an image must not build a run mode around finding one. An engagement does not need it either (see §2, engagement): the platform starts the estate before it starts you and puts this container on the estate's own network, which is what removed the tunnel and the userspace WireGuard terminator every image used to carry.
5. Versioning
schema_version is in both task.json and the result you write. A client that checks it can refuse a version it does not understand instead of misreading one. A client that ignores it will keep working until the first breaking change and then fail in a way nobody can diagnose — so check it.

The standard number and the schema version are two different things, on purpose. CTFY-0001 names this document for as long as it exists; schema_version names the wire format it currently specifies. Editing this page to say something clearer does not move either. Adding a field does not move the schema version — a client that ignores an unknown key is unaffected. Only a change that could make a conforming client misread something does, and §6 is where that is recorded.

This standard's version is its schema version: the number in the header moves exactly when schema_version does. An additive change is recorded under the version it was made in, with its own date, and does not move it.

6. Revision history
The revision history is part of this document's header — the same metadata the platform renders above §1 — so it is stated once. Every version is listed there with its date and whether it breaks a conforming client, and so is every additive change made inside a version, each with its own date. If a change is not there, it did not happen: an implementer needs to be able to diff what they built against what is specified now, without reading a repository they may not have.

The platform keeps every earlier version readable at its own address (/docs/standards/CTFY-0001/v1), so a client written against one can be checked against the text it was written from.

Why the name. The obvious short names in this space are taken, several inside this exact field: ACI is SWE-agent's Agent-Computer Interface, ATP is an active IETF draft, and MCP / A2A / ACP / ANP are all live agent protocols. Prefixing with the project is what PEP, JEP, SIP and TIP do.

7. Checking your image against this document
Before you register an image:

ctfy agent check ghcr.io/you/your-agent:v1
It runs both halves the platform runs — a manifest read, and one local dry run to see whether your container writes its result file — and it uses the platform's own rule module rather than a second implementation, so a pass here is the answer registration will give you.

Two things it will tell you plainly rather than hide:

Without a docker daemon it does the manifest half only, and says so. The most common failure is an image that writes no result file, and that half is the one a daemon is needed for.
It applies no size limit. How large an image a deployment will accept is that operator's setting, not a property of this document, and a number guessed here would fail images the platform would take.
--json emits the findings and the verdict and nothing else, for CI.
