# Competition 001: proj_001–proj_022 耗时复盘

范围仅限 HotMouse competition_001 的 proj_001 至 proj_022。项目成败以平台比赛条目状态为准：14 题 succeeded，8 题 failed。计时来自 HotMouse SQLite 中的 challenge started_at/finished_at、worker_task_history，以及各项目 Pi JSONL；模型 API 尝试来自 red-token usage_logs。所有数据库以只读模式查询。没有读取或分析 proj_023 及之后项目的内容。

## 总体耗时

22 题累计墙钟时间约 340.8 分钟（5 小时 41 分）。按每个时间片当时的 worker 主任务归属分段，约 187.8 分钟在执行、38.1 分钟在 Dispatcher 决策、18.4 分钟在结果总结/提交、7.5 分钟在目标分类，另有 89.0 分钟没有活跃任务记录。分段互斥，因此合计与比赛墙钟时间一致。实际工具调用区间去重后只有 15.6 分钟；多数执行耗时在模型思考、生成和等待 API。

使用的本地模型共记录 639 条 assistant 消息和 636 次工具调用；执行任务共 70 条，Dispatcher 总结/提交任务共 62 条。执行调用的 5 分钟上限被触发至少 21 次；任务结果中有 22 条明确报执行超时。中断恢复时 11 次记录为 JSON/响应格式错误，另有多个总结再次触发 90 秒上限。重复总结、格式修复和重新规划继续消耗比赛时间。

## 成功题

- proj_001 / g-32（8.2 分钟）：下载 ELF 附件后，字符串扫描即可找到候选值。候选值第一次出现在工具输出后约 3 分 48 秒，项目才完成；原因为执行被中断后又跑只读总结，再由协调器提交。此题说明即使是直接字符串题，发现结果后仍可能等待整段总结流程。
- proj_002 / g-09（9.9 分钟）：下载邮件后离线解码 JavaScript/PowerShell 混淆，提取嵌入的值。两个步骤都接近 5 分钟，第二步依赖中断总结。
- proj_004 / g-35（6.2 分钟）：从网页接口发现隐藏命令，再发一次请求取得结果。中间做了不必要的端口扫描和 socket 方向测试，并有 4 次总结调用；提早检查网页脚本/API 可更快。
- proj_005 / g-08（11.6 分钟）：从 Shell 脚本做逆序与 Base64 变换后成功提交。约 5.7 分钟花在 Dispatcher 决策；由于“先下载、再分析、再提交”被拆成多次规划，简单静态题也用了较多规划时间。
- proj_006 / g-31（4.6 分钟）：先确认 Velocity 模板注入，再用同一已验证入口读取结果，路径直接。
- proj_007 / g-05（2.1 分钟）：用 RSA 中 `n-1` 的结构快速解密，是全组成功题中最快的一题。
- proj_008 / g-07（1.6 分钟）：附件题，直接分析并解密，整体很快。
- proj_009 / g-13（5.4 分钟）：识别自定义压缩格式并还原明文；取证后很快转向本地文件分析。
- proj_010 / g-33（17.6 分钟）：在排列群离散对数上尝试了多条路线，最终独立求解 B 侧并恢复明文。单项模型请求和执行都很长，适合先做小样本算法门槛测试，再决定是否投入完整求解。
- proj_011 / g-06（8.1 分钟）：逐位恢复 RSA 素数后解密成功；初次计算因 90 秒工具上限中断，第二条路径完成。探测 Python 包缺失也占了少量时间，宜一开始用已有标准库或单一自包含实现。
- proj_013 / g-15（11.2 分钟）：根据 RSA 各分量补回缺失模数并解密。平台元数据和附件入口探测先发生 404/超时，之后才进入有效重建步骤。
- proj_016 / g-14（17.3 分钟）：先从可执行文件运行时内存及 ECS 碎片入手，再用静态数据确认并重组。中间有多个 5 分钟执行中断和总结，最终仍完成；应把可重复的内存/静态检查尽早合并成固定脚本。
- proj_018 / g-36（10.2 分钟）：确认 Python 黑名单规则后使用单引号绕过读取文件。约 2.7 分钟是实际探测工具时间，模型解释与数轮总结构成大部分其余耗时。

## 失败题

- proj_003 / g-12（20.0 分钟）：约 11.1 分钟执行、5.3 分钟恢复总结/提交。第一次元数据/附件步骤和第二次分析步骤超时；后续已下载 UPX、脱壳并在工具输出中出现格式正确的候选值，但没有生成平台已接受的 flag 记录，项目最终超时失败。这是已经接近做完、却被步骤边界和总结流程拖过截止时间的直接例子。
- proj_012 / g-16（20.0 分钟）：约 15.0 分钟执行、3.0 分钟决策。LCG 求解中尝试的模数/状态模型不成立，随后做跨字符和另一条逐位路线；多次各跑满 5 分钟仍没有恢复 flag。工具区间只有约 18 秒，说明主要成本在反复模型推理和等待响应，而不是脚本运行。应先用少量样本验证方程与数据排列，再扩大搜索。
- proj_014 / g-21（63.8 分钟）：其中约 53.7 分钟没有活跃任务。此前下载了 628 KB Go RPG 并确认可用 Go 符号工具；最后约 2 分钟只完成工具盘点，没有继续逆向。项目随后按 20 分钟比赛上限失败。空档原因无法从留存信息证实，但它占此题总墙钟绝大多数。
- proj_015 / g-22（20.0 分钟）：约 16.9 分钟执行。已经下载并确认 ChaCha20 工具链，之后主要花在 stripped ELF 静态分析、运行行为和猜测密钥派生，未取得密钥、nonce 和密文。red-token 为本题记录了 36 条非 200 尝试，其中 18 条为 503，累计底层请求耗时约 15.4 分钟；底层请求可能跨失败转发重叠，不能直接当作额外墙钟时间。说明 provider 可用性也消耗了本题预算。应先确认可用模型后端，并设定静态/动态分析停止条件。
- proj_017 / g-29（20.0 分钟）：约 18.0 分钟执行、94 秒去重工具时间。抓包、C2 流和客户端已定位，但三段 flag 中仍有部分未恢复；多个 5 分钟任务围绕不同流量和密钥路线展开，其中一次 EZRAT 解密脚本运行约 76 秒。问题是范围太大、证据链长，在尚未完整验证第一段时又分支尝试其他流量。应先建三段位置清单，按抓包可见性逐段验证并及时停止无进展分支。
- proj_019 / g-10（20.0 分钟）：约 11.8 分钟执行、7.1 分钟决策，是这组中决策最久的失败题。已本地确认 RestrictedUnpickler 的 dotted-path 白名单绕过，但没有把该构造串成远端可用的完整 payload，也没有取得 flag。其间 Web 前端、TCP 服务和附件交互的假设多次切换；需要先确认真实协议和入口，再对本地最小化 payload 做端到端验证。
- proj_021 / g-20（20.1 分钟）：约 14.5 分钟执行、4.9 分钟决策。字符白名单探测工具本身累计运行约 4 分钟；一轮约 90 秒后又做重复扫描，且并发与串行观测相互矛盾。到截止时没有写出或验证编码器/载荷。应减少成对探测、逐个复测不一致字符，并以少量探针立即建立可执行编码器。
- proj_022 / g-19（33.5 分钟）：约 30 分钟没有活跃任务。空档前已逆推出 64 位候选 key，并将其发给 1337 服务；响应文本里出现一个 flag 格式的候选片段。但没有结构化的成功结论、HotMouse flag 记录或平台 accepted 状态，因此不能把它当成已通关。留存数据库显示执行在 07:01:27 后停止，到 07:31:24 才有恢复任务；中间空档使 20 分钟比赛期限过去。必须改进候选值即时持久化与提交。

## 提速优先级

1. **先让 flag 离开模型执行循环。** Worker 从已完成的工具响应中发现格式符合当前题目规则的候选 flag 时，先把候选值和响应证据可靠写入项目，再由协调器提交和确认。模型结构化总结只负责补充分析。proj_003 和 proj_022 都显示候选值已出现在本地输出，却没有平台接受记录。候选提取需要保留来源证据并以比赛平台的 accepted 响应为唯一成功判据，避免把 banner 或无效字符串当成成功。
2. **让超时总结短而有上限。** 38 次中断总结提示包含约 18 KB 中位长度上下文，并且最多再触发格式修复；多条总结本身又打满 90 秒。先要求原 session 只返回短 JSON 和证据路径；若失败，则基于已有工具记录生成最小 blocker 事实，不重复总结，也不无限占用 Dispatcher。
3. **把 5 分钟执行额度花在高信息量步骤。** 先查看附件、网页自动索引、服务协议等已有材料，用短检查确认算法/格式假设；上传与解析在一个脚本内完成；第一条可行核心路径成功后立即输出事实与候选 flag。对 003、012、015、017、019、021 这类难题，避免在证据不足时平行追加猜测路线。
4. **压缩规划回合。** 简单附件题优先把获取、识别与可逆变换写成可执行的连续工作，并减少确认 toolchain、重复拉元数据、重复端口/服务探测。proj_005 花 5.7 分钟决策但实际变换很直接；proj_004、007、009、020 也存在可跳过的探测步骤。
5. **为实际利用率增加服务存活与恢复监控。** 两段长空档合计约 83.7 分钟。运行比赛时让 coordinator 周期性告警“项目 running 但 worker、Dispatcher 均无活动”；恢复服务后根据剩余 challenge deadline 自动给出实际剩余时间，不要让已无可用时间的项目等待到下个轮次才收尾。
6. **先做 provider 健康检查，再评估并发。** 22 题里记录到 62 条 503 和 6 条 429（尝试级日志）。失败题 g-22 尤其集中出现 503。赛前预热决定/执行模型、连续采样首 token 延迟和 503 率；不稳定时切换健康后端或降低请求量。比赛原并发为 1，主机记录为单 CPU，因此不要直接把并发升到 2 或 3；先用相同题型 A/B 测量吞吐与超时率。
7. **把探测实验设计成有停止条件的实验。** g-20 的重复字符扫描用掉约 4 分钟却产生矛盾结果。限制扫描范围，保存每次原始输入/响应，对异常值做一次串行复测；在确认允许字符集后立即生成小型编码载荷，而非重复全量扫描。

## API 请求统计口径

red-token usage_logs 中匹配到这 22 个项目的 799 条 DeepSeek 后端尝试日志、689 个 request_id。633 条 HTTP 200 尝试的时长合计约 204.3 分钟；166 条非 200 尝试合计约 62.7 分钟，其中包括 503、上下文取消产生的 499、权限/请求问题及限流。每个前端模型调用可能产生 failover 尝试，这些底层时长会重复计入；499 通常是调用已被取消，不等于后端自身又额外卡住一段时间。因此 API 请求耗时不与上面的墙钟分段相加。HTTP 200 的首字节延迟中位数约 3.3 秒，p95 约 20.2 秒；长时间执行主要由多轮模型调用叠加，不是单次网络往返。

报表只保留项目、时间、任务类型、HTTP 状态与耗时，没有写入 prompt、附件内容、API 凭证或 flag 值。
