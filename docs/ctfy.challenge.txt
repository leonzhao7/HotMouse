A challenge package is a directory: the files that make one challenge, as its author uploads them. This standard says what the platform does with one — which files it reads, which it refuses, how it starts them, how it hands each team its answers, how it grades, how it checks the package works, and who sees it afterwards. If you are writing a challenge for this platform, this page is the contract.

How to read it. Two kinds of rule appear below, and they are different on purpose:

A refusal is applied when you upload. The upload is turned down, with a code and the reason, and nothing is stored. Every refusal code is in the appendix (Part B), with the clause it comes from.
An audit finding is advice. The audit reads the package and reports findings with a rule code (META005, STRUCT002, …) and a severity, error or warning. On an upload the audit is evidence for the person reviewing it, never a gate. On the platform's own curated corpus an error fails the build. Every rule code is in the appendix (Part A), with the clause it comes from.
Check a package before you upload it, on your own machine, with no platform and no token:

ctfy authoring check ./my-challenge
It runs the audit and the refusals an upload would meet that need no competition, and it says which version of this standard it checked against. ctfy authoring check <competition> ./my-challenge additionally asks a platform for its own verdict, including the competition's own rules.

ctfy authoring init ./my-challenge --stack python-flask writes a package that already satisfies everything here.

1. Directory structure
1.1 The root
A package is any directory holding a metadata.yaml. Its id is the directory's name; an id: written in metadata.yaml is ignored (and is an audit finding, META005).

An uploaded package's id is never the name you chose. The platform mints one, AUTHORED-<8 hex>, and your directory name is kept as the upload's slug — the label you replace a pending upload by (§8).

1.2 Files the platform reads
path	required	what it is
metadata.yaml	always	the challenge's description and its questions (§2)
docker-compose.yml	for web and pwn (STRUCT001)	the services that run per team (§3)
services/<name>/	when a compose service has build: (STRUCT003); each build context needs a Dockerfile (STRUCT004)	the source of each service
solution/exploit.py or solution/Dockerfile	unless the item is question-and-answer only (STRUCT002)	the reference solution (§6)
solution/WRITEUP.md	on an upload (authoring_writeup_missing)	the author's writeup, step by step (§6.1); never served to a team
attachments/	for pwn, reverse, crypto, misc unless question-and-answer only: at least one file at its top level (STRUCT010)	files every team downloads; *.tpl files are rendered per team (§4.3)
audit-allowlist.yaml	no	allowlist: [{rule, path, line?, reason}] turns a matching audit error into a warning
params/	no — written at run time by a seeder (§4.5)	never shipped
The platform reads no other file by name. There is no ignore file: the CLI's packer leaves out .git, __pycache__, node_modules, .venv and .DS_Store, and lists anything else it leaves out (§7.3).

1.3 Reserved names
Three compose service names are a contract with the platform, and a service by one of these names is treated as that sidecar (§4):

service	role
flag-rotator	writes each team's minted answers into the box (§4.2)
attachment-builder	builds a per-team file into attachments/ (§4.4)
seeder	plants a value through the running app and publishes params/ (§4.5)
1.4 What a category requires
category: (§2.1) decides what the audit expects to find:

category	needs docker-compose.yml	needs attachments/	may be question-and-answer only
web	yes	no	no
pwn	yes	yes	no
reverse	no	yes	yes
crypto	no	yes	yes
misc	no	yes	yes
An item is question-and-answer only when its category is misc, it has no docker-compose.yml, and every question carries a static answer:. Such an item cannot be uploaded (§2.7); it exists in the curated corpus only.

1.5 What an upload refuses about the archive
An upload is a .tar.gz (a plain .tar is accepted too) or a .zip, told apart by its first bytes rather than its name, and it is attacker-controlled input, so it is read member by member before anything is written. One unsafe member refuses the whole archive. Both formats are read into the same list of members and every rule below applies to either.

A single common top-level directory is stripped; after that, metadata.yaml must be at the root (archive_no_metadata). An archive with no members is archive_empty.
Every member must be a regular file. A symlink, a hard link, a device or a fifo is archive_member_not_a_file — in a zip, read from the entry's Unix mode or Windows reparse-point attribute.
A file's path may appear only once (archive_member_duplicate).
In a zip: no encrypted member (archive_member_encrypted); every name flagged UTF-8 or valid UTF-8 (archive_member_name_encoding); only stored and deflate compression, and a local header that names the same file as the central directory — otherwise the upload cannot be read.
Every path must stay inside the package: not empty (path_empty), not absolute (path_absolute), not starting with ~ (path_home_directory), no .. segment (path_escapes), no empty or . segment (path_dot_segment), no backslash or NUL (path_backslash_or_nul).
Under attachments/: no hidden name (attachment_hidden), no deeper than 16 levels (attachment_too_deep), no control character, bidi override or backslash in a name (attachment_name_unusable), at most 2 000 files (attachments_too_many).
The size limits are in §7.4.
2. metadata.yaml
2.1 Top-level keys
The file is a YAML mapping. A file that does not parse, or is not a mapping, is META000, and the audit then reports nothing else.

key	type	required	default	checked by
name	string	yes	—	META002
description	string	yes	—	META002, META007, META010, META014
difficulty	easy | medium | hard	yes	—	META002, META003
tags	non-empty list of strings	yes	—	META002, META004
questions	non-empty list (§2.2)	no	one dynamic question, id flag, prompt "Capture the secret"	META006, META008, META009, META010, META014, META015, META018
category	web | pwn | reverse | crypto | misc	no (generated packages always write it)	web when omitted (legacy packages)	META011
network_topology	simple | engagement	no	simple	META012 (§3.6)
vpn_backend	openvpn | wireguard, only with engagement	no	openvpn	META016
entry_urls	list of absolute http, https, tcp or udp URLs (tcp and udp need a port)	no	[]	META013; with engagement also META017, META019
edge_service	string: the service a player connects to	no	inferred (§3.6)	—
awd	mapping: an attack & defence gamebox	no	—	AWD001–AWD010 (§3.9)
patch	mapping: the patchable surface	no	—	PATCH001–PATCH006 (§3.9)
standard	CTFY-0002/<version>	no	the current version	META020 (§2.8)
Any other top-level key is META005. The retired keys of an older schema — flags, vars, public_vars, flag_path, flag_inject, id, origin, provider, provider_config, hint_levels — get a hint naming their replacement.

⚠️ The platform's own reader ignores unknown keys rather than refusing them, so a misspelled key is caught by the audit and by nothing else.

An upload's name is shown on every surface that lists a challenge (the catalog, the scoreboard, mail, the CLI), so the upload door asks two things of it:

at most 100 characters (authoring_name_too_long);
no character in Unicode categories Cc, Cf, Zl or Zp: no newline, tab, zero-width or text-direction character (authoring_name_unusable, which names each one by its code point).
A corpus challenge never meets the door, and every corpus name would pass it.

The description is shown to every team before they start, so:

it states the goal and never the vulnerability class, the technique or an internal endpoint (META007, a warning — it matches words, and a word list cannot be a gate);
it never paraphrases a gated question's prompt (META010);
it never reaches for an answer (META014, §2.6).
2.2 Questions
Each entry of questions: is a mapping. Its keys:

key	meaning	default
id	the question's id (§2.4)	required
prompt	what the team is asked; non-empty	required
answer	a fixed answer: a string, or a list for a multi-select	absent
choices	the options of a select question	absent
requires	ids of questions that must be solved first (§2.5)	[]
format	flag or raw	flag
match	how a submission is compared (§5.1)	{mode: exact, case_sensitive: false}
check	a sidecar that decides (§5.4): service, cmd, timeout_s (30), poll (false), poll_interval_s (60)	absent
answer_from	seeder: the challenge supplies the answer (§4.5)	absent
scores	capability or reporting — which axis of the board it pays	capability
Any other key, a missing id or prompt, a wrong type or a malformed check: is META006. An unknown scores: is META018 — never a quiet fall-back to capability.

⚠️ A malformed question is dropped by the platform's reader, not refused, so the audit is where you learn of it.

2.3 How a question's mode is inferred
A question never declares its mode. It is inferred from which keys it carries, in this order:

check: with no answer and no choices → checker: a sidecar decides (§5.4).
answer_from: seeder with no answer and no choices → seeded: the challenge supplies the answer per instance (§4.5).
no answer and no choices → dynamic: the platform mints a fresh answer for every team (§4.1).
a string answer, no choices → static.
a string answer with choices → single-select.
a list answer with choices → multi-select.
Anything else — choices without an answer, check: beside an answer, an answer_from other than seeder — has no mode and is META008 (or META006 for check: beside an answer).

2.4 Question ids
An id matches ^[a-z][a-z0-9_]*$ and is unique within the package (META006). It becomes a file name (/answers/<id>) and an environment variable (ANSWER_<ID>, the id upper-cased), which is why the alphabet is that narrow.

2.5 requires:
Each id in requires: must name another question of the same package (META009), never the question itself, and the graph must have no cycle. A question whose requires: is non-empty is gated: it is not shown until those are solved, and the description may not paraphrase it (META010).

2.6 Prompts and per-instance values
The description and each prompt may use Jinja placeholders of exactly one name, param: {{ param.port }}. The values come from params/prompt.json, which a seeder writes per instance (§4.5). A text with no {{ or {% is shown unchanged.

Nothing else is available, and nothing else is the language: a placeholder is {{ param.<name> }} or {{ param["<name>"] }}, one level deep, with a name that does not start with _. Any other name (answer among them — a prompt is published to the team, and an answer in it would be published too), a filter, a call, a test, a {% … %} block other than {% raw %}, arithmetic or a text that does not parse is META014, refused at upload (authoring_template_unsupported) and never rendered. Prose that means its braces literally — a server-side-template-injection task quoting {{7*7}} — wraps them in {% raw %}…{% endraw %}.

2.7 What an upload requires of the questions
An upload is refused unless:

it has at least one question the platform can read (authoring_requires_a_question);
at least one question is answered per instance — dynamic, checker or seeded (authoring_requires_minted_answer). Beside it, a static or select answer may be uploaded for a fact with no per-instance value; it is the same for every team, so prefer a minted answer wherever the value can be minted. A static answer on an upload always has a wrong-attempt cap, and the reviewer is shown which questions use one;
every question's mode can be inferred (authoring_question_mode_invalid);
no static answer is expected from the platform (authoring_static_answer_delivered): the platform mints only per-instance answers, so a template interpolating answer.<id> or a service declaring ANSWER_<ID> for a static question is refused;
something in the package delivers each answer (authoring_answer_undelivered): a dynamic answer through a running service or a per-team file (attachments/*.tpl or an attachment-builder); a checker or seeded answer through a running service. A service under a compose profiles: does not count as running;
in a competition with no end date, at least one answer is minted per instance (standing_needs_minted_answer);
the description, every prompt and every attachments/*.tpl are in the template language (§2.6, §4.3; authoring_template_unsupported).
2.8 Declaring the standard
A package may say which version of this standard it is written to, in one line:

standard: CTFY-0002/1
Absent: the package is checked against the current version, and the audit result says not declared, checked against v1. Nothing has to be added to a package written before this key existed.
A version the platform supports: the package is checked against that version. If a newer one exists, the audit result lists the versions it has not caught up with and what each changed — advice, never a refusal.
Anything else — a version this platform does not know, or a value not of the form CTFY-0002/<n>: an upload is refused (standard_unsupported), naming the versions the platform supports; the audit reports it as META020.
The audit result records the declared value and the version actually checked against, on every surface that shows an audit: the author's page, the review queue and ctfy authoring check. ctfy authoring init and every template write the current version.

3. Compose
3.1 Which file, and when it is ruled on
Only docker-compose.yml at the package root is read, and only it is run. An upload rules on it before anything is stored, and every refusal is collected and returned together. A file that does not parse is compose_unparseable; one that is not a mapping is compose_not_a_mapping. A package with no compose file is not refused here.

⚠️ The rule is an allow-list that fails closed: a key the platform does not know is refused, not passed through. It buys the declarative surface only — a Dockerfile's RUN still runs on a worker when the image is built (§7.1, §7.5).

3.2 Top-level keys
Allowed: services, volumes, networks, name, and any key starting with x-. Anything else is compose_top_level_key — include:, configs:, secrets: and version: among them (version: is also the audit's COMPOSE002). A network declared external: true is compose_external_network.

A top-level network may set driver: bridge and internal: true, and nothing else; any other key or driver is compose_top_level_key. internal only separates segments: whether a box reaches the internet is the worker's firewall and the competition's policy, read from x-ctfy-internet (§7.1) and never from internal. ipam: is read and refused: the worker chooses an uploaded challenge's addresses, so a subnet cannot capture the worker's own resolver, router or LAN (compose_network_ipam). For the same reason a service may not fix its own address on a network — ipv4_address, ipv6_address or link_local_ips is compose_network_address; reach a service by its name. That includes labels: — and a network label in a namespace the platform writes itself (traefik., com.docker., ctfy.llm-relay) is also compose_network_label, named for what it would do: the node marks an instance's network for its LLM relay with ctfy.llm-relay, so an upload setting it would choose where the relay joins. Top-level volumes are §3.4's.

x-ctfy-internet (§7.1) and x-ctfy-sharing (§7.6) are the two extensions the platform reads. Their shapes are COMPOSE010 and COMPOSE011.

3.3 Service keys
Allowed: build, cap_add, command, depends_on, deploy, dns, entrypoint, environment, expose, healthcheck, hostname, image, labels, links, network_mode, networks, ports, profiles, read_only, restart, shm_size, stop_grace_period, stop_signal, sysctls, tmpfs, tty, ulimits, user, volumes, working_dir. A tmpfs is charged to the service's own memory limit.

Refused with their own code:

key	code	why
container_name	compose_container_name	the platform names every container itself
extra_hosts	compose_extra_hosts	host-gateway is a route to the worker
Every other service key is compose_service_key — including privileged, pid, ipc, devices, security_opt, userns_mode, cgroup_parent, runtime, cap_drop, env_file, mem_limit, cpus, init, platform and a service-level x-*.

3.4 Values the upload checks
key	allowed	code
cap_add	NET_ADMIN, IPC_LOCK, NET_RAW, NET_BIND_SERVICE	compose_capability
cap_add with NET_ADMIN or NET_RAW (or privileged)	only on a service with no ports: and no ctfy.edge. label that joins none of the file's external networks — directly or through network_mode: service:<name>	compose_capability_on_shared_network
sysctls	net.ipv4.ip_forward	compose_sysctl
labels	anything not starting traefik., com.docker. or ctfy., plus the three ctfy. declarations ctfy.service.protocol, ctfy.edge.domain and ctfy.edge.vhosts	compose_label
networks.<name> (a service's)	aliases only; an address key is compose_network_address	compose_service_network_key
network_mode	none, or service:<name>	compose_network_mode
volumes (short form)	a named volume; a bind only to a path inside the package; modes ro, rw, nocopy only	compose_bind_outside, compose_volume_option
volumes (long form)	type: absent, volume, tmpfs, or bind inside the package; options read_only, bind.create_host_path, volume.nocopy, volume.subpath (inside the volume), tmpfs.size, tmpfs.mode only	compose_volume_type, compose_bind_outside, compose_volume_option
volumes (a bind's mode)	writable only when the source is exactly attachments or params; any bind source, and any build path, inside attachments/ or params/ is refused (a build path may not be either)	compose_bind_writable, compose_path_in_writable
top-level volumes entry	empty, or a mapping whose only key is driver: local	compose_named_volume, compose_named_volume_key, compose_volume_driver_opts, compose_volume_driver
build (string)	a path inside the package	compose_build_outside
build (mapping) keys	context, args, dockerfile, additional_contexts, network	compose_build_key
build.context, build.dockerfile	a path inside the package	compose_build_path_outside
build.network	none or default	compose_build_network
A path stays inside the package only when it is a plain relative path: letters, digits, ., _, - and /, not starting with /, with no .. segment and no empty one (a trailing / is fine). Anything else — an absolute path, ~, a backslash, and any :, so a remote build context such as https://…, git@host:repo or ssh://… — is outside it. An additional_contexts entry may instead be service:<name>.

deploy: may hold resources.limits.cpus and resources.limits.memory and nothing else; any other key under it (reservations, placement, limits.pids, …) is compose_service_key.

Variables. Compose resolves $ references against the worker's environment, so every key and every value in the file is read, under any key: a $ is accepted only as half of $$ (a literal $), or, as a service's environment: value, in exactly ${NAME} or ${NAME:-<default>} with a default holding no $ or {. Any other $ — $NAME, ${NAME-x}, ${NAME:?x}, a nested or unterminated reference — is compose_interpolation. A bare entry is a read too: - NAME or NAME: with no value passes the variable through, which a service's environment: may do and build.args may not. Either way NAME is one the platform hands an instance: ANSWER_<ID>, CTFY_SERVICE_URL_<SERVICE>, CTFY_INSTANCE_URL, or the LLM_* credential. A .env at the package root, which Compose reads without being told to, is compose_dotenv.

The other allowed keys' values are not inspected by the upload. ports: is allowed and rewritten when the box starts (§3.6).

3.5 Resources and health
The upload does not require resource limits; the audit expects them (COMPOSE006): every service sets deploy.resources.limits.cpus and .memory.

The platform applies a budget to every instance of an uploaded package, all its services together: by default one CPU and 2 GiB of memory, set by the operator. It is split over the services the stack starts — each weighs what it declares, or one CPU and 512 MiB when it declares nothing, and when the weights exceed the budget every service is scaled down in proportion — and written over the package's own values, with at most 512 processes per service. A one-shot profiles: service (the attachment-builder) runs alone and is held to the whole budget. So a package that needs its budget concentrated in one service declares limits that say so. A worker counts the whole budget when it places the box.

The upload asks the same question first. The memory (deploy.resources.limits.memory) the services of the stack declare, summed, may not exceed the budget the platform would apply (authoring_memory_over_budget): a package asking for more would be squeezed at run time and may crash, so it is refused instead. Declared CPU (deploy.resources.limits.cpus) over the budget is only advised about (authoring_cpu_over_budget): CPU is compressible and the runtime caps every instance to the budget anyway, so it slows the box rather than breaking it. A service declaring nothing is not counted, and the check advises about it (authoring_resources_undeclared); ctfy authoring check <dir> with no competition compares against the platform's default budget. Published packages are not re-judged.

Every service needs a healthcheck (HEALTH001), except a one-shot that others wait on with condition: service_completed_successfully and the attachment-builder. docker compose up --wait is how the platform knows a box is ready, so a service with no health check is ready the moment it starts.

3.6 Network topology
network_topology: (§2.1) chooses one of two shapes.

simple (the default). Every ports: entry is removed when the box starts; each service that declared one is the team's entry. It gets a random host name on the platform's ingress and is joined to the ingress network beside its own default. HTTP is routed by host name; a service labelled ctfy.service.protocol: tcp is routed as TLS by SNI. The audit reads that label (STRUCT012, STRUCT013, STRUCT014, STRUCT022); at least one service must publish a port (COMPOSE003). How a team reaches a tcp service — TLS by SNI on port 443, a port of its own, or the VPN — is the competition's choice, not the package's. A service labelled ctfy.service.protocol: udp speaks datagrams: it is never routed by host name, and is reached on a port of its own, or through the VPN when the competition chooses that for it; TLS by SNI, which cannot carry UDP, reads as a port of its own.

A port is the service, its container port and its transport; the host side of an entry is never read, so an entry repeated, or differing only in its host side, is one port. An uploaded package publishes at most 8 distinct ports of tcp and udp services together — each can take a port of the node's own, which every challenge on the node shares — by default, an operator setting (authoring_public_ports_over_cap), and at most 32 distinct ports in all, HTTP included (authoring_routes_over_cap). The upload refuses past either, and a start refuses again before it takes any port.

engagement. The team reaches the box through a VPN rather than the ingress. Unless the package declares its own VPN service, the platform adds one, plus a resolver (edge-dns), on a dmz network it adds too, and joins the edge service to it. The edge is edge_service: if given, else the only long-running service, else the only one that publishes a port; otherwise the start fails. Every other ports: entry is removed. entry_urls hosts must be names the team's own machine can resolve through the tunnel (META017, META019). A package that declares its own VPN service is held to NET001–NET005; every engagement estate's declared zone (ctfy.edge.domain) is held to NET006.

An estate names itself with two labels: ctfy.edge.domain (its zone) and ctfy.edge.vhosts (names under it). Every service carrying ctfy.edge.vhosts is an entry point, and its names resolve inside the tunnel to that service's own address — so an estate may route every name through one edge by Host, or give each entry point its own container. A service without the label stays internal. The zone is the edge's ctfy.edge.domain, or the first other service's when the edge declares none. The tunnel reaches only the dmz network: the edge is always joined to it, and any other entry point must name dmz in its own networks: — the platform does not join it for you, and its names are not served until it is there (NET007). A name declared by two services resolves to the edge if it is one of them, else to the first in the file (NET008).

3.7 How the box is started
Per team, the platform runs docker compose build and then docker compose up -d --wait over docker-compose.yml plus an override of its own. An uploaded package is always built from source — never from a pre-built image of it. A build that fails fails the start; so does a service that never becomes healthy.

Before anything starts, every image the start created a container from — built or pulled — is read: an image label starting traefik., or starting ctfy. but not one of the three declarations of §3.4, refuses the start (image_label). A LABEL in a Dockerfile reaches the container exactly as a compose labels: entry does.

3.8 What else the audit reads in compose
COMPOSE001 (services: is a mapping), COMPOSE004 (no Dockerfile but the rotator's bakes an answer), COMPOSE005 (no ANSWER_ build arg), COMPOSE007 (no service hard-codes its own public URL — the platform injects it as CTFY_SERVICE_URL_<SERVICE> and CTFY_INSTANCE_URL), COMPOSE008 (every COPY/ADD source exists), COMPOSE009 (a RUN that starts a database also stops it).

3.9 Attack & defence gameboxes
An awd: block makes the package a gamebox for an attack & defence match, and patch: declares what a defender may change. Their audit rules are AWD001–AWD010 and PATCH001–PATCH006. The checker contract between the platform and a gamebox (put / get / check) is not part of this version; it will be its own standard.

4. Answer delivery
4.1 The channels, and when each runs
A dynamic answer is minted by the platform for every team, and it never leaves the platform except into that team's box. There are four ways a package receives one, and they run at different moments of a start:

order	step	channel
1	the package is copied for this team	—
2	attachments/*.tpl are rendered	templates (§4.3)
3	attachment-builder runs, before the services	builder (§4.4)
4	docker compose up -d --wait	rotator (§4.2), seeder (§4.5)
5	params/prompt.json and params/answer.json are read	seeder (§4.5)
Every minted answer is in the compose environment as ANSWER_<ID>; a service receives it only by naming it in its own environment:.

4.2 flag-rotator
The rotator is a one-shot service that names each ANSWER_<ID> it owns in environment: and writes each value, verbatim, to a shared volume — the scaffold writes /out/<id>. The service that needs the answer mounts that file at /answers/<id> and waits on flag-rotator: condition: service_completed_successfully. Write the file in place: a single-file mount binds an inode, so a rename leaves the app reading the old one.

The audit: the rotator is required for every dynamic answer no checker, builder or seeder delivers, and it names exactly those (STRUCT006); some service consumes it (STRUCT007); it publishes no port (STRUCT008); no service mounts /answers/<id> for a static or unknown id (STRUCT009).

4.3 Templates: attachments/*.tpl
A file under attachments/ ending in .tpl is rendered per team, as a Jinja-syntax template, before anything starts. Two names are available: answer.<id> (the minted values) and instance.id. The language is the one in §2.6 with these names, plus an integer slice of a value ({{ answer.flag[0::2] }}); comments and {% raw %} are allowed, anything else — a filter, a call, {% if %}, {% for %}, {% include %} — is not. The result drops the .tpl suffix and the template itself is not served. A template that does not render fails the start.

The audit: a template names only dynamic ids that exist (STRUCT017) and is in that language (STRUCT018; refused at upload as authoring_template_unsupported); a package with no compose file delivers every dynamic answer through some template (STRUCT011).

4.4 attachment-builder
For a per-team file a template cannot produce — a binary built around the answer. The service carries profiles: ["ctfy-builder"] (STRUCT019), names the ANSWER_<ID> it needs, bind-mounts ./attachments to /out (STRUCT021) and publishes no port (STRUCT020). The platform runs it once, before the services, as docker compose --profile ctfy-builder run --rm --no-deps --build attachment-builder, with 300 seconds to finish. A non-zero exit or a timeout fails the start.

4.5 seeder and params/
A seeder is an ordinary compose service that runs after the app is healthy and talks to it through the app's own interface. It has two uses:

plant a minted answer: it names ANSWER_<ID> in its own environment:, and that id is then off the rotator's list (STRUCT006);
supply a per-instance answer, for a question with answer_from: seeder (§2.3). It writes, through a ./params:/out bind mount:
params/answer.json — an object keyed by question id; each value is the answer (a string, or for contains the answer set of §5.3);
params/prompt.json — an object of values the prompts render as {{ param.<name> }} (§2.6);
params/manifest.json — for the package's own judge; the platform never reads it.
A params/ file that is missing, is not a JSON object, or is a symlink is read as empty: the instance still starts, and a seeded question on it cannot be answered. The audit requires the seeder's Python to parse (SOURCE005).

4.6 What may never carry an answer
No Dockerfile but the rotator's bakes one (COMPOSE004), no build argument is named ANSWER_* (COMPOSE005), and no source file under services/ carries a literal FLAG{…} (SOURCE001).

5. Grading
5.1 match:
field	values	default
mode	exact, contains, judge	exact
case_sensitive	boolean	false
An unknown mode is META015. case_sensitive changes contains only; an exact comparison is always case-sensitive.

5.2 exact
By mode:

dynamic and seeded: both sides stripped of whitespace, then compared as strings; a match with the FLAG{…} wrapper removed from either side also counts.
static: both sides stripped, compared as strings.
single-select: the value must be one of choices and equal the answer.
multi-select: a list, or a string split on commas and whitespace; every part must be one of choices, and the set must equal the answer's.
A list sent to a question that takes one value is refused — not graded — and costs no attempt.

5.3 contains
Only on a seeded question (META015). The seeder's value for it is an answer set, {"any": [...], "none": [...], "at_least": N} (a bare string is a set of one). A submission is accepted when at least N (default: all) of any appear in it as substrings and none of none appear as a word. An empty set, an empty submission or an at_least outside 1..len(any) is wrong.

5.4 Checker and judge
A checker question has no answer for the team to submit: the package's own sidecar (check.service, running check.cmd) prints this question's minted token when the team has achieved the effect it checks. With match: {mode: judge} the team submits a value and the sidecar is given it as one more argument; the answer is accepted only if the sidecar prints this question's own token. A submission longer than 4 096 characters is not passed. The judge needs check: (META015), must exist in compose and name the question's ANSWER_<ID> (STRUCT015), and publishes no port (STRUCT016).

When the platform cannot run the judge — the worker is gone or silent, out of time — the submission is neither right nor wrong, and costs no attempt.

5.5 Wrong-attempt caps
Questions whose answer space is bounded are capped, counted in wrong answers since the last reset by an organiser, and checked before grading, so the cap cannot be used as an oracle. The defaults: single-select 3, multi-select 10, static 10, seeded 10, judge 10. A dynamic or checker question is never capped. An operator may change the caps.

5.6 The author's own team
Your own team is graded on your own upload — pressing submit is the only way to check from outside that it is answerable — and scores nothing for it: no solve is recorded, so it takes no first blood and decays no points.

6. Reference solution and smoke
6.1 The solution
Every package that runs ships one, as solution/exploit.py or solution/Dockerfile (STRUCT002). A Dockerfile is built from the package root with docker build -f solution/Dockerfile and run with its own entrypoint; the language is yours. Otherwise solution/exploit.py runs in the platform's ctfy-exploit-runner image, which carries Python, requests and the ctfy package, so it needs nothing installed.

An exploit.py imports ExploitBase and run_exploit from ctfy.challenge.exploit (EXPLOIT002), defines class Exploit (ExploitBase) with a run method (EXPLOIT003), and calls run_exploit under if __name__ == "__main__": (EXPLOIT004). It must parse (EXPLOIT001), and it must rediscover each answer the way a team would — it may not read ANSWER_*, /answers/, params/answer.json or params/manifest.json in its own process (EXPLOIT007). params/prompt.json is the team's own view and is available as self.params.

An upload also carries its writeup, solution/WRITEUP.md: one numbered step per action — what to do, and what you see when it works. The platform's AI pre-check follows it on a fresh instance, to say whether the challenge can be solved the way its author says. An upload or a new version without one is refused (authoring_writeup_missing), and so is one with nothing in it (authoring_writeup_empty); a version stored before this rule keeps working. It is the author's and the reviewers', never a team's: the platform serves a team only attachments/ (§4).

A solution in another language is a solution/Dockerfile. It is built like a service (§7.5) and held to the same contract (§6.2); the audit's EXPLOIT rules read exploit.py only.

# solution/Dockerfile — the default runner, said explicitly
FROM ctfy-exploit-runner
ENTRYPOINT ["python3", "solution/exploit.py"]
6.2 The contract
Input. The target as two arguments, <host> <port>, and as CTFY_TARGET_HOST / CTFY_TARGET_PORT; each sibling service as CTFY_SERVICE_URL_<SERVICE>.
Output. One line Q[<question_id>]: <value> on stdout per answer found. run_exploit prints these.
Exit code. 0 captured; 1 ran and failed; 2 crashed; 3 captured nothing; 4 could not reach the target.
What the solution must print: every dynamic answer except a checker's, and every seeded one. A dynamic value must equal the minted one, after stripping whitespace; a seeded one is only checked for being present.

6.3 Where it runs
Non-root (65534:65534), on a read-only root filesystem with a writable /tmp (512 MiB), with every capability dropped and no-new-privileges, 1 024 processes, 2 GiB of memory and 2 CPUs. The package is copied into /chal, which is the working directory. It is attached to the box's own compose networks — or, for an engagement package, to a tunnel the way a team connects — and to nothing else: no internet, no docker socket, no host directory.

6.4 The smoke
A smoke is a real start of the package on a worker, followed by its solution, followed by teardown — the way a team would meet it:

the package is placed on the worker;
answers are minted; the box is started as in §3.7 and §4.1 — templates, builder, build, up --wait, health;
for engagement, the tunnel is brought up as a team's would be;
the solution is built (if it is a Dockerfile) and run;
what it printed is compared with what was minted (§6.2);
the box is torn down and its images removed.
verdict	meaning
solved	every answer was found and right
unsolved	the box ran and the solution missed or got an answer wrong
estate_failed	one of your own services failed to build or become healthy, or the solution image failed to build
malformed	the package could not be read
errored	the platform could not finish the run — never your fault, and never charged to you
6.5 What the log shows you
Each run's log lists its steps — build, up, health, reach, exploit, grade — each ok, failed, timed_out or skipped, with the exit code, the tail of the output, and for grade what was printed against what was expected. Only your own services' output and your own solution's are recorded, and the worker's names, paths and secrets are replaced by <node>, <tree>, <tmp>. A step keeps 8 KiB, a log 64 KiB, and the last 10 logs of an upload are kept. ctfy authoring smoke-log <competition> <id> prints them.

6.6 When a smoke runs
On upload, within a per-person allowance over a rolling 24 hours that the operator sets (0 turns it off); a competition with automatic review uses its team quota instead. A smoke on upload is evidence for the reviewer, never a gate on publishing. A published upload is smoked again from time to time, and a failure is mailed to its reviewers once per change from passing to failing.

6.7 Smoking on your own machine
ctfy authoring smoke --local ./my-challenge runs the same solution in the same image against your box. It exits 0 solved, 1 wrong or nothing captured, 2 the box or the solution image failed, 3 the package is missing or malformed.

7. Runtime environment
7.1 The network
While a box runs, whether it reaches the internet is the competition's policy: allowed, denied, or decided per challenge. Under the per-challenge policy the package states what it needs:

x-ctfy-internet:
  required: true
  reason: The app fetches exchange rates at start.
(COMPOSE010: a mapping with only required and reason; a reason is required when required is true, at most 500 characters.) A denied box has no route out and no outside DNS. The smoke always runs denied.

While an image builds, on a worker that runs uploaded code, a build cannot reach another network's published port. build.network may be none or default, never host (§3.4).

Uploaded code is fenced off the worker, in its build, its smoke and every running box: it keeps the internet (so apt, pip and npm work), DNS, its own networks and the challenge's own public URL, and reaches nothing else of the machine — not the worker's own addresses or gateways, not its LAN, not cloud metadata (169.254.0.0/16, 100.100.100.200), not another team's box. Build and service logs are yours in full. A worker that cannot hold the fence refuses the build or start (fence_unavailable in the smoke log) rather than run it unfenced. An uploaded gamebox does not run in classic AWD, whose match network joins every team's box; it runs as AWD+, or once graduated into the corpus (§9.8). It is refused when it is added — to a classic AWD competition's set, or as its match's gamebox — not when its box fails to start (awd_classic_authored_gamebox).

The reference solution never reaches the internet (§6.3).

7.2 Executable bits
The owner-execute bit of each file travels with the upload and is restored when the package is written on a worker: an executable is 0755, anything else 0644. No other mode bit, owner or timestamp survives. An archive that records no execute bit at all is read as not recorded: a file that starts with #! or is an ELF binary is then made executable.

7.3 Packing
The CLI (ctfy authoring upload and check) packs a directory itself: it leaves out .git, __pycache__, node_modules, .venv and .DS_Store, refuses to pack symlinks and special files, and names each thing it left out.

7.4 Size limits
limit	value
the archive as uploaded	the operator's setting, 64 MiB by default
entries in the archive	2 000 (archive_too_many_entries)
one file	64 MiB (archive_member_too_large)
all files together	128 MiB (archive_unpacks_too_large)
files under attachments/	2 000, at most 16 levels deep
The platform measures the unpacked size while it reads, so an archive that expands past the limit is stopped without being unpacked. A path has no length limit of its own.

7.5 Build time, and the review of what a package runs
A service is built from its own Dockerfile on a worker reserved for uploaded code. Any FROM image is allowed. The worker holds no credential to the platform's own registry.

What a package runs is reviewed by a person before it is published: the compose file, every Dockerfile, everything under solution/ and inside a build context, and any executable or archive under attachments/. A package with any of these needs that review once, and a replaced package arrives unreviewed.

7.6 Sharing one environment
An organiser may let several teams stand on one running environment of a challenge instead of one each. The package says whether that is safe; the platform never guesses:

x-ctfy-sharing: shareable        # or: per-connection
shareable — several teams may use one environment (read-only, stateless, or otherwise unharmed by a neighbour). per-connection — the challenge isolates every connection itself (a forking or nsjail entry service), so sharing the environment shares nothing a player can touch. Absent is undeclared: sharing it is the organiser's call and they are warned, never blocked. (COMPOSE011: one of the two words.) A challenge with the engagement topology cannot be shared at all.

A shared environment is started once for its group of teams and its minted answers are generated once, so every team of the group submits the same value.

8. Versions and revisions
8.1 Every upload is a version
Every tree you store — the first upload, each re-upload while it waits, each proposed revision — is kept as a version, numbered v1, v2, … for the challenge, with its files and each file's execute bit, your change note, its smoke run and its review verdict. A tree identical to the current one, execute bits included, stores no new version. Any two versions can be compared, and each downloaded. A version's submission time is what a player's report, a re-check's failure and every "since this version" rule count from.

One version waits for review at a time: storing a new one while another waits withdraws the waiting one, which stays in the history. Only a version waiting for review can be withdrawn by its author (version_not_withdrawable); a version the platform recorded without its files cannot be compared or downloaded (version_tree_not_kept).

8.2 Replacing a pending upload
Upload again under the same slug (the directory's name) while the first is still pending, and it is replaced: the same id, a new version, the previous one withdrawn and kept (§8.1) — and not charged against your pending cap. An upload that has been approved cannot be replaced (authored_challenge_already_reviewed): revise it (§8.3). One that was rejected stays on record; upload the new attempt under a new name.

8.3 Revising an approved upload
Any of its recorded authors may propose a revision: a whole new tree for the same id. A revision passes every rule an upload passes. It is reviewed as a diff against the live tree, by a reviewer of the competition, and applied by a platform administrator.

Question ids may only grow. A revision that drops a question the platform serves today is refused (revision_drops_question); a missing questions: counts as the default flag question.
A revision identical to the live tree, execute bits included, is refused.
One proposal per upload: a new one replaces the one waiting.
A revision changes the files only. The declarations, the contributor agreement and the destination stay the upload's.
Applying swaps the published directory whole, so a box already running keeps the tree it started with. The version and the smoke verdict move with the new tree; the smoke verdict starts empty.
In a competition with no end date, the new tree must still mint an answer per instance (revision_curated_into_standing).
8.4 Which version players get
One version is live: a new box is built from it, and a box already running keeps the tree it started with. Only a platform administrator changes which one — never an author — by applying an approved proposal or rolling back to an earlier approved version, now or once every running competition that includes the challenge has ended. Every switch is recorded, with who made it and why.

Only an approved version can be made live (switch_not_approved, switch_upload_not_approved), and not the one already live (switch_already_live).
A rollback needs a reason (switch_needs_reason), and question ids only grow, so a version missing a question the live one serves is refused (switch_drops_question).
A new tree's execution surface is confirmed again (switch_exec_surface_unreviewed), and in a competition with no end date it must mint an answer per instance (switch_curated_into_standing).
A switch cannot wait for a competition with no end date (switch_never_ends); one switch waits at a time (switch_already_scheduled); and a switch whose live version changed while it applied is refused (switch_changed). A waiting switch that can no longer apply when its moment comes is skipped, and its administrator is told.
A competition may lock its challenges' versions while it is in play (lock_challenge_versions): a switch or rollback is then refused (version_switch_locked, version_rollback_locked). A platform administrator may force one — only an administrator, and only with a reason (version_lock_force_not_admin, version_lock_force_needs_reason) — and the reason is recorded with the switch.
9. Who can see it
9.1 Review
An upload starts pending. A reviewer — a platform administrator, a competition's organiser, or someone the organiser named a reviewer — approves or rejects it; a rejection carries a note. Approving does not publish it.

Once its files are on the platform, the verdict no longer decides who can see it, so it is not changed there: approving, rejecting and withdrawing a verdict are refused (review_verdict_in_use) until the upload is blocked. A revision (§8.3) is still reviewed.

A competition may review automatically instead: it decides on the smoke (§6.4) — solved approves, publishes and curates the upload — and asks three more things of an upload, each a refusal:

something in the package runs, so there is something to smoke (smoke_nothing_to_run);
the package is not byte for byte one already uploaded or already in the catalog (duplicate_of_upload, duplicate_of_catalog);
where the competition has a model read every upload for text aimed at the agents that will solve it, the package is small enough to be read whole (authoring_too_large_to_review), and holds no such text the model can quote (authoring_prompt_injection).
9.2 Publishing
Publishing writes the package into the platform's catalog — the files on disk are the publication — and is a separate step from approving (publish_*). It requires an approved upload and, where the package runs anything, the review of §7.5.

An organiser of a competition curating it, or an administrator, may take a published upload down, with a reason that is recorded (unpublish_*), and restore it later (republish_*). Taking it down leaves the upload's row, so restoring it needs no new upload.

A platform administrator may instead retire an upload whose files are on the platform (retire_not_on_platform): it is no longer offered, and unlike taking it down nothing running is stopped and its authoring credit stays; its solves keep their points unless the administrator chooses to remove them. A retired upload leaves every competition and its catalog release, and no competition may add it (curation_retired) nor the catalog release it (catalog_release_retired) until an administrator offers it again.

9.3 Into a competition
A published upload is played in a competition that curates it — lists it among its challenges (curation_*). A competition whose set is a whole catalog directory cannot curate one by one (curation_bucket_competition), and neither can a competition whose set follows another competition's, which never inherits player uploads (curation_followed_competition). A competition that runs a classic AWD match takes no uploaded gamebox (awd_classic_authored_gamebox): its match network joins every team's box (§7.1). While a competition that locks its challenges' versions is in play, adding a challenge to it or taking one out needs a confirmation and a reason, recorded per challenge (curation_locked_needs_reason).

An upload belongs to the competition it was uploaded to — its home. Its home, and that competition's own test, may always curate it. Another competition may curate it only when the home is public — an upload to an invitation-only competition stays there (curation_private_home_event) — and only when a platform administrator or one of the home's organisers adds it (curation_not_home_organiser). An upload already in another competition when this rule arrived, or when its home becomes invitation-only, is removed from that competition, on its record.

9.4 The public catalog
Published is not public. Until it is released to the catalog (catalog_release_*) an upload is seen only inside the competitions curating it: by their organisers, by its authors, by administrators, and by registered players once that competition has started. Released, it joins the catalog anyone can practise from. An upload to an invitation-only competition is never released while that competition stays invitation-only (catalog_release_private_competition), and taking an upload offline withdraws its release too: published again, it waits for a new release.

9.5 The evaluation pool, and what never leaves
An original upload whose authors allowed it to be used for evaluating AI agents may choose the destination eval_only (destination_needs_eval_use, destination_needs_original). It is then kept out of the catalog, the credits and the public statistics; it starts only in a competition that is not public and curates it, and its files are read only by administrators, its authors, and that competition's members.

Whatever the destination, a team sees what the package serves — attachments/, the description, the prompts and its own box — and never the package's source. Minted answers never leave the platform.

9.6 Credit
An upload names its uploader, by display name, only when they chose to be credited. The name is withheld while a competition the reader can see is playing it live, and wherever the upload's own event withholds that entrant's identity.

9.7 Declarations
Where a competition names a contributor agreement, an upload declares the licence it grants (declaration_license), whether it is original or a port (declaration_provenance) — a port names its source as an http(s) address (declaration_source_missing, declaration_source_not_web), and an original names none (declaration_source_not_a_port) — and whether AI helped write it (declaration_ai_assisted). An upload may not grant more than the team's captain granted when accepting the agreement (declaration_grant_beyond_team). A declaration nobody made is stored as not declared, never as an answer.

9.8 Into the corpus
An upload may graduate into the platform's curated corpus when it is approved and published, its own solution solved it on the last smoke, its licence allows redistribution, and it is not in the evaluation pool (graduation_*). Its tree must not carry its own root LICENSE or CREDITS.md, which graduation writes (graduation_file_collision).

9.9 Folding duplicate uploads into one
An author who uploads one challenge several times — a new slug for each iteration — leaves several uploads of it. A platform administrator may merge each other upload into the one kept. The merged upload is an alias: it leaves every competition's set, and no competition may add it while it stays merged (curation_merged); its versions, smoke runs and authorship stay where they are. Every merge is recorded, with who made it and why, and an administrator may undo it; nothing that left a set comes back by itself. The merged upload takes no new version either: an upload under its slug, a replaces: naming it, its dry-run check and a revision of it are each refused, naming the upload kept (upload_merged) — the author uploads with replaces: <the upload kept> instead. Each of its authors is told of the merge, and of an undo, in their inbox.

Only another upload of the same challenge can be merged: one in the same competition, under the same name:, by the same team or a shared author (merge_not_same_challenge), and never the upload into itself (merge_self).
There are no chains: an upload already merged is not merged again (merge_already_merged), the upload kept may not itself be merged (merge_target_merged), and an upload others are merged into is not merged until they are moved (merge_has_aliases).
A merge waits while the upload has running environments (merge_running_instances) or a revision waiting for review (merge_open_revision).
A merge needs a reason (merge_needs_reason). Where a running competition holds the upload but not the one kept, merging takes the challenge from its entrants, and needs a confirmation as well (merge_live_competition).

2026-10-14 — §2.1: an upload's name is at most 100 characters and carries no control, format (text-direction, zero-width) or line-separator character (authoring_name_too_long, authoring_name_unusable). Every corpus name passes.
2026-10-17 — §3.5: the platform now holds an uploaded challenge's whole instance to a CPU and memory budget the operator sets (one core and 2 GiB by default), split over its services and applied over whatever the package declares, with 512 processes per service. A package's own limits are the weights of the split.
2026-10-18 — §3.5: the services' declared memory, summed, may not exceed that same budget (authoring_memory_over_budget); declared CPU over it is advice only (authoring_cpu_over_budget); a service declaring no limit is not counted and is advised about (authoring_resources_undeclared).
2026-10-18 — An optional standard: key in metadata.yaml (§2.8) says which version a package is written to. Absent, the package is checked against the current version; an unsupported version is refused (standard_unsupported, META020); the audit result records both the declared and the checked version.
2026-10-19 — §7.6: an optional x-ctfy-sharing key in docker-compose.yml says whether several teams may stand on one environment of the challenge (shareable, per-connection); absent is undeclared, and COMPOSE011 checks its shape.
2026-10-23 — §3.4: a top-level volumes: entry is empty, or names driver: local and nothing else. driver_opts — which turns a named volume into a host bind via type: none, o: bind and a device — another driver, and any other key are refused (compose_named_volume, compose_named_volume_key, compose_volume_driver_opts, compose_volume_driver). Every corpus named volume is the empty form.
2026-10-28 — §2.1, §3.6: ctfy.service.protocol may be udp (STRUCT012; a pwn package's one raw service may be it, STRUCT014), and entry_urls may name a udp://host:port (META013, the port required). A udp service is reached on a port of its own, or through the VPN; it is never reached by TLS and SNI. Additive: every package valid before stays valid.
2026-10-28 — §3.2, §7.1: an upload may not choose its own addresses — a network's ipam: is refused (compose_network_ipam), and so is a service's ipv4_address, ipv6_address or link_local_ips (compose_network_address); reach services by name. Every uploaded package's build, smoke and running box is fenced off the worker, its LAN and cloud metadata, keeping the internet and its own networks. An uploaded gamebox does not run in classic AWD. Three corpus entries pin a subnet; the corpus is not uploaded.
2026-10-28 — §3.4: a service may give a network only aliases (compose_service_network_key; an address key stays compose_network_address), and a service label in the ctfy. namespace is compose_label unless it is ctfy.service.protocol, ctfy.edge.domain or ctfy.edge.vhosts. Every corpus package already writes only these.
2026-11-02 — §3.6: an engagement estate may have several entry points. Every service labelled ctfy.edge.vhosts is one, and its names resolve to that service's own address, not the edge's; a service without the label stays internal. The audit warns when such a service is not on the dmz network (NET007) or two services declare one name (NET008). Additive: an estate that labels only its edge resolves exactly as before.
2026-11-02 — §1.5: an upload may also be a .zip, told apart by its first bytes, never its name, and held to every rule a tar is. Asked of new bytes only: a version stored before keeps working. The corpus is not uploaded and is not asked.
