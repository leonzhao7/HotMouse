## 4. 建议按这个顺序提速

1. **缩短决策与总结，限制格式修复。** 112 条决定任务中有 7 条 failed、17 条 interrupted。50 次中断后的总结请求以及 29 次仅修复总结 JSON 的请求，记录的模型调用时长分别累计约 **26.2 分钟、11.1 分钟**，含并行区间，不能作为独立墙钟节省量相加。建议决策以 45–60 秒的小预算只给少量可验证动作；复杂密码推导交给执行。总结目标 20–30 秒，只返回关键事实、证据路径和候选值；最多一次格式修复，失败后用已有工具记录构建最小结果，避免 g-18 式两次连续 5 分钟规划。
2. **结果一出现就可靠保存、验证并提交。** 候选值要带原始来源，核对题目 flag 格式与多 flag 要求，并以平台正确响应为成功判据。完整报告可随后生成。21 题的结果出现至收尾共 34.9 分钟，是值得压缩的区间；不能保证全部节省，g-31 的拒绝响应就要求继续验证。g-07 的 7.62 分钟等待最适合做回归用例。
3. **简单附件题合并获取、识别、求解和交付。** g-05 花 11.23 分钟、g-07 花 8.99 分钟，数学/字符变换本身很快；不要把 VPN、重新取列表、附件盘点、重算和提交分别拆成新的长规划回合。平台地址、已下载附件和经过验证的解题脚本应让后续步骤直接复用。
4. **按进展动态停损，调整题目顺序。** 第 8–10 分钟仍没有新增可验证事实时，限制继续追加猜测分支；已有接近完成的利用链可继续。回看这轮，如果 10 道满额失败题各少花 10 分钟，会释放约 **100 分钟**，但这只是回放估算。统一把所有题限时改为 10 分钟会截断 g-05、g-31、g-11、g-29 四道最终成功题，所以需要按进展停损。排序应考虑附件可得性、方案确定性和预期分数/分钟：g-39、g-40 虽标 hard，实际分别用 4.66、8.14 分钟拿到 1000 分，比优先尝试但连续失败的 g-04/17/18/26 更值得早做。
5. **固定 Python 解释器与能力清单，减少重复盘点。** 赛前缓存一次可用工具、导入命名空间和最小能力验证；根 venv 和题目专用 venv 都用明确的解释器路径。优先修复 Crypto/Cryptodome 混淆和 g-37 的解释器错用。需要更好的原生调试/.NET 分析能力时再预装 gdb、相应 .NET 工具；本轮证据不足以把失败单独归因于缺包。
6. **为探测设置响应预算和停止条件。** g-20、g-17、g-26 的工具时间有较多网络等待。已有协议或静态附件时，避免全量重扫；采用少量能否定假设的探针，对异常一次复测，得到结论后立即进入利用或停止该分支。

## 5. 统计限制

- 当前 red-token `usage_logs` 最早留存时间为 **2026-11-11 01:16:53 UTC**，本轮比赛对应的 11 月 10 日记录已经不在该表内。因此没有本轮 HTTP 503/429 次数、首 token 延迟或重试耗时证据；不能用现在的 API 日志解释过去的慢调用，也不能把缺失记成“没有错误”。指标 CSV 不输出伪装成 0 的 API 数据。
